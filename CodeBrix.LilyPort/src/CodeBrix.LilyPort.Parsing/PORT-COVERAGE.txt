PORT-COVERAGE -- CodeBrix.LilyPort.Parsing
==========================================

Deliberate divergences from LilyPond's lily/parser.yy and lily/lexer.ll, with the
reason. Read this before assuming any rule action is a literal translation. The
grammar, tables, driver and lexer machinery are covered by tools/parser-baseline/
and the Parsing test suite; this file records the RULE-ACTION layer, which began
with the RAG13 + RAG1 session of 2026-08-03.


-------------------------------------------------------------------------------
THE VALUE MODEL (every action follows it)
-------------------------------------------------------------------------------

  Upstream declares `#define YYSTYPE SCM`; the port's semantic values are plain
  `object` over the CodeBrix.LilyScheme value types:

    SCM_UNSPECIFIED   ->  Unspecified.Instance
    SCM_UNDEFINED     ->  DefaultArgument.Instance   (Guile's missing-argument
                          marker plays SCM_UNBNDP's role exactly)
    SCM_EOL           ->  Nil.Instance
    SCM_BOOL_T/F      ->  bool
    symbols           ->  Symbol (interned; scm_is_eq is ReferenceEquals)
    strings           ->  CLR string as produced by the lexer; MutableString is
                          accepted wherever a value is TESTED for stringness
    numbers           ->  the SchemeNumber tower (long / BigInteger / Ratio /
                          double), so scm_divide of exacts stays exact

  Bison's C skeleton runs every action with $$ already initialized to $1. An
  upstream body that never assigns $$ (including the empty `{ }` bodies) is
  therefore ported as an explicit `return values[0]`.

-------------------------------------------------------------------------------
LOCATIONS
-------------------------------------------------------------------------------

  The RuleAction delegate receives BOTH the per-symbol spans (@1..@n, the
  `locations` array) and their join (@$, `location`). Upstream actions use the
  two distinctly -- an error in `lilypond_header_body: ... SCM_TOKEN` points at
  @2 -- and a port that only had the join would silently degrade hundreds of
  later action sites. Added in this session, while only three actions existed.

-------------------------------------------------------------------------------
MID-RULE STACK ACCESS (added with RAG3)
-------------------------------------------------------------------------------

  A mid-rule action reduces as an EMPTY production, so its values array is
  empty -- but Bison lets it reach the OUTER rule's earlier components, and the
  book/bookpart/score mid-rules use that: $@5 and $@6 read $1 (the book being
  built) and $@7 both reads AND ASSIGNS $1 (`$1 = scm_cons (ly_make_module (),
  $1)`). Bison compiles a mid-rule's $k after n preceding symbols to the stack
  slot k - n relative to the top; the port exposes exactly that as
  ParseContext.StackValue(depth) / SetStackValue(depth, value), where $1 after
  one symbol is depth 0. Driver semantics, not a divergence -- added to
  Driver/LalrParser.cs when the first three actions needed it, the same way
  per-symbol locations were.

  EXTENDED WITH RAG18: StackLocation(depth), the same access for @k rather
  than $k. A mid-rule's own @$ is the point-span Bison gives an empty rule, so
  an action that reports an error at @1 -- markup_scm's does, and hands the
  same span to three MYBACKUP calls -- needs the stack's location, not its
  own. Same convention, same reason, same file.

-------------------------------------------------------------------------------
THE DRIVER'S LAZY LOOKAHEAD (added with the RAG8-RAG10 session)
-------------------------------------------------------------------------------

  Driver/LalrParser.cs now reproduces Bison's yybackup entry test
  (yypact_value_is_default): a state whose ONLY action is its default reduction
  reduces WITHOUT reading a token. This is behaviour, not optimization -- rule
  actions switch the lexer's mode, and an eagerly-read token is lexed in the OLD
  mode. It is the faithful, driver-level fix the wave-1/wave-2 sessions recorded
  as owed (their per-action analyses called it "Bison's yydefact behaviour");
  DriverTests pins both halves (a default-only state reduces at Reads == 1 with
  no lookahead; a mode-switch head reduces before its following token is read).

  Consequences for earlier groups' notes, each revised in place below:
  - the RAG7 revert machinery's PushBackLookahead compensation is retired
    (simple_revert_context no longer pushes back; MYBACKUP's own guarded
    pushback is upstream's macro, unchanged);
  - the RAG4 "EAGER-LOOKAHEAD SITES" analysis, the RAG6 music_embedded_backup
    per-site analysis, the RAG11 markup-pop note and the RAG12 mode-head caveat
    are all RESOLVED: the port now reads the lookahead exactly where upstream
    does. The analyses stay as the record of why the driver had to change.

-------------------------------------------------------------------------------
THE HOST SEAM (Actions/IParserHost.cs)
-------------------------------------------------------------------------------

  Everything an action reaches through Lily_parser, Lily_lexer or Guile is
  behind IParserHost, the same seam pattern as ILexerHost and the Engine's
  Context.ContextFactory. Notable foldings, each recorded on the member's doc:

    lookup_identifier / lookup_identifier_symbol -> one LookupIdentifier(string);
        the symbol form differed only in taking the already-interned symbol.
    scm_module_variable + scm_variable_ref -> TryModuleVariable(module, name,
        out value); every action site used the two together.
    MAKE_SYNTAX(name, ...) -> MakeSyntax("scheme-name", ...): the constructor is
        named by its SCHEME-side dashed name (partial-music-function), because
        scm/ly-syntax-constructors.scm is the already-vendored side of the seam.
    MY_MAKE_MUSIC -> MakeMusic + SetMusicProperty: music creation consults the
        music-descriptions table, which lives in the Scheme layer, so a
        parser-built music object must come from the host or it would silently
        lack its type's own properties -- the half-reproduced-declaration defect
        shape the engine sessions kept finding.
    unsmob<Score>, unsmob<Book>->paper_, Text_interface::is_markup(_list),
        Lily::markup_function_p / define_markup_command_internal / key_p,
        loc_on_copy -> host predicates/operations, because the engine did not
        have those types or tables when RAG1 landed (Book and Score exist as
        of RAG3; the members keep their shape).
    Lily::key_list_p -> IsKeyList; scm_object_property (x, "is-grob?") ->
        IsGrobSymbol (the property is DATA set by set-object-property! in
        scm/define-grobs.scm, so only the host can answer); Input::warning ->
        Warning(location, message), which does not move the error level.
    Lily_parser::default_duration_ -> DefaultDuration (RAG2); the Syntax::name
        constructor lookup START_MAKE_SYNTAX conses without calling ->
        SyntaxConstructor (RAG5); Lily::scorify_music -> ScorifyMusic (RAG3).
    Lily_lexer::push_markup_state -> PushMarkupState (RAG18), the last of the
        mode pushes; and the Lily::name variables that markup expressions cons
        WITHOUT calling -> LilyImport (RAG18), which is SyntaxConstructor's
        opposite number for the (lily) module.

-------------------------------------------------------------------------------
PER-ACTION DIVERGENCES
-------------------------------------------------------------------------------

  start_symbol: EMBEDDED_LILY $@1 embedded_lilypond   (RAG1)

    Upstream stores $3 through the `SCM *retval` %parse-param and leaves $$
    alone. The port has no out-parameter: LalrParser.Parse RETURNS the start
    symbol's value, so the action returns $3. The other start alternative
    (`start_symbol: lilypond`) is unchanged -- callers of a file parse ignore
    the value either way, exactly as upstream ignores retval there.

  symbol: embedded_scm_bare   (RAG13)

    Upstream's failure path generates an UNINTERNED symbol via
    `scm_make_symbol (to_scm ("undefined"))`. The port uses Symbol.Generate,
    LilyScheme's uninterned-symbol maker, whose printed name carries a
    uniquifying suffix ("undefined" alone upstream). Cosmetic: the symbol is
    reached only after a reported parse error, and what matters -- that it is
    fresh and cannot collide with a real binding -- is preserved.

  text: / simple_string: embedded_scm_bare   (RAG13)

    The error-recovery value `scm_string (SCM_EOL)` is ported as CLR
    string.Empty rather than a fresh MutableString. Both satisfy every string
    test downstream; nothing mutates an error-recovery string in place.

  try_string_variants   (ParserActionHelpers)

    Takes a CLR Func<object, bool> predicate where upstream takes an SCM
    procedure. The one caller ported so far passes Guile's symbol?; action
    sites in later groups whose predicate IS an SCM value (function_arglist
    family) wrap it over IParserHost.Call at the call site.

  get_header   (ParserActionHelpers)

    Comes from lily/lily-parser.cc, not parser.yy -- the one epilogue-adjacent
    helper that lives in another upstream file. Ported over the host seam
    (LookupIdentifier / MakeModule / ModuleCopy) rather than over Guile module
    calls.

  post_event_cons   (ParserActionHelpers)

    Ported directly over Engine MusicObject/Prob rather than through the host,
    because every operation it needs (is_mus_type, the property alist,
    get/set_property) is already real in the Engine. Srfi_1::append_reverse and
    ly_append are implemented locally as AppendReverse/Append -- reducing a rule
    must not depend on an interpreter being alive.

  embedded_lilypond: duration post_events %prec ':'   (RAG2)

    parser->default_duration_ is IParserHost.DefaultDuration -- Lily_parser state
    behind the host seam, like the lexer modes. Duration is the ported value type
    (a readonly struct), so the property assignment copies by value exactly as
    upstream's `*unsmob<Duration> ($1)` does. With no post events the body, like
    upstream, never assigns $$ -- a bare duration stays a Duration. NOTE: RAG6's
    music_embedded carries a SIMILAR-LOOKING duration post_events body that
    genuinely differs (it always makes the NoteEvent); do not copy this one.

  reverse_music_list / add_post_events   (ParserActionHelpers.Rag2)

    Ported from parser.yy's epilogue directly over Engine MusicObject/Prob, the
    same choice as post_event_cons and for the same reason. The Lily_parser *
    parameter became the IParserHost -- upstream passes it only to feed the
    MAKE_SYNTAX / MY_MAKE_MUSIC macros. MAKE_SYNTAX (event_chord, *p->origin (),
    post) reads the music's `origin` property and uses it WHEN it is a boxed
    SourceSpan, else the default span -- Music::origin answering
    dummy_input_global for unstamped music. The REAL host's MakeMusic/LocOnCopy
    must stamp `origin` with a boxed SourceSpan or these locations degrade
    silently. Music::warning is Flower's Warn.Warning at the origin's string
    form. scm_last_pair and the two-list scm_append_x are implemented locally
    (LastPair / AppendInPlace), like the scm_reverse_x family.

  book/bookpart/score bodies (RAG3)

    unsmob<Book> / unsmob<Score> are DIRECT casts to the Engine's Book and
    Score, ported for this group -- the OutputDef precedent from RAG1. The
    RAG1 host members IsScore/BookHasPaper predate the types and keep their
    shape; retiring them for direct casts is an integration-time decision
    recorded in the RAG3 session report. Smob protect/unprotect calls are
    dropped throughout, as everywhere in the port.

    scm_reverse_x over the collected output-definition list feeds
    add_output_def through `as OutputDef`: upstream's unsmob returns a null
    pointer for a non-output-def entry and pushes it anyway, and the port
    stores null identically rather than throwing.

  Lily::scorify_music   (score_items)

    A host member, ScorifyMusic -- the toplevel-music-functions fold lives in
    the vendored Scheme layer (scm/lily-library.scm), so the REAL host must
    dispatch to the vendored scorify-music, not merely wrap the music in a
    Score; the scripted test host does only the ly:make-score tail and says
    so.

  init_papers / push_paper / pop_paper / set_paper   (ParserActionHelpers.Rag3)

    From lily/lily-parser.cc, over the host seam like get_header. set_paper is
    scm_set_car_x -- it MUTATES the pair at the top of $papers in place, so a
    host whose LookupIdentifier returns copies would silently lose the write.
    get_paper (the read side) is NOT ported here; it belongs to RAG4's
    paper_block/output_def_head actions.

  context_def_spec_block: / context_def_spec_body: ...   (RAG5)

    Context_def::make_scm () is `new ContextDef ()`, and unsmob<Context_def> /
    unsmob<Context_mod> / unsmob<Music> are C# type tests -- the direct
    Engine-type-cast convention set by RAG1's OutputDef actions. The block's
    `td->origin ()->set_spot (@$)` is ContextDef.SetSpot(location): the port
    has no Input smob, so the definition stores the parser's SourceSpan
    opaquely, the same convention as MusicObject's origin.

  context_prefix: CONTEXT/NEWCONTEXT symbol optional_id optional_context_mods   (RAG5)

    START_MAKE_SYNTAX is NOT MakeSyntax: upstream builds
    `ly_list (Syntax::name, args...)` without calling anything, and
    FINISH_MAKE_SYNTAX (RAG6's contexted_basic_music) applies it later with a
    location. The port adds IParserHost.SyntaxConstructor(name) -- the
    procedure-lookup half of that seam -- and conses exactly upstream's list.
    The names are the Scheme-side dashed ones (context-find-or-create,
    context-create), verified against the vendored ly-syntax-constructors.scm.

  optional_context_mods: context_modification_mods_list   (RAG5)

    scm_append_x is implemented locally as ParserActionHelpers.AppendInPlace
    (the one-list-of-lists overload, ParserActionHelpers.Rag5.cs), destructive
    like the original. Safe here because ContextMod.GetMods returns fresh
    copies -- upstream's own comment at the rule -- and a ContextMod test pins
    that freshness.

  revert_arg_backup: revert_arg_part / simple_revert_context: symbol_list_part   (RAG7)

    Upstream reaches both reductions WITHOUT a lookahead token read (they sit in
    default-reduction states -- "symbol_list_part ... can be parsed without
    lookahead" -- and MYBACKUP guards its pushback with yychar != YYEMPTY).
    ORIGINALLY the port's driver read its lookahead eagerly before every
    reduction and both actions compensated by opening with PushBackLookahead().
    -> REVISED in the RAG8-RAG10 session: the driver now defers the read exactly
    as Bison does (see THE DRIVER'S LAZY LOOKAHEAD above), so the compensation
    in simple_revert_context is REMOVED -- there is no lookahead to push back at
    a default-only reduction -- and revert_arg_backup's pushback is just
    MYBACKUP's own guard, which is upstream's macro verbatim. The wrong-mode
    caveat this entry used to carry is retired with it.

  MYBACKUP / push_extra_token   (ParserActionHelpers.Rag7)

    Upstream pushes tokens by their Bison-exported NUMBERS; the port pushes by
    NAME and resolves the number through the running ModalScanner's symbol
    table (UseSymbols/Terminal) -- the same numbering the scanner lexes with,
    so there is no second copy to drift. A token source that cannot resolve
    names makes PushExtraToken throw rather than push a guess.

  try_word_variants   (ParserActionHelpers.Rag7)

    Takes a CLR Func<object, bool> predicate where upstream takes an SCM
    procedure, following try_string_variants. The one caller ported so far
    passes IParserHost.IsKeyList (the fixed primitive Lily::key_list_p from
    scm/c++.scm); action sites in later groups whose predicate IS a semantic
    value wrap it over IParserHost.Call at the call site. scm_string_split is
    rendered over CLR string.Split -- safe because is_regular_identifier has
    already vetted the shape.

  property_path_dot_warning   (ParserActionHelpers.Rag7)

    Input::warning becomes IParserHost.Warning -- a diagnostic that must NOT
    raise the error level, unlike parser_error. An integer key in a dotless
    path would be a wrong-type error upstream (ly_symbol2string) and is an
    InvalidCastException here -- same failure, new spelling.

  get_paper / get_midi / get_layout   (ParserActionHelpers.Rag4)

    From lily/lily-parser.cc over the host seam, completing the $papers family
    the Rag3 file began: get_paper is the READ side -- "Return a copy of the
    top of $papers stack, or $defaultpaper if the stack is empty". A $papers
    binding that is neither unset, empty nor a pair is a wrong-type error at
    scm_car upstream and an InvalidCastException here -- same failure, new
    spelling. get_layout will be wanted again by the markup score-lines rules
    (parser.yy 4162 and 4333); it lives here, reuse it.

  assign_context_def   (ParserActionHelpers.Rag4)

    From lily/output-def.cc -- the one helper this group calls that upstream
    keeps in a third file. Upstream asserts AND guards its unsmob; the port
    keeps the release-build behaviour (a non-Context_def is silently ignored),
    and every call site has already tested the value. A bare `\context { }`
    stores under the empty symbol, ContextDef's default name.

  output_def_head / output_def_body   (RAG4)

    Output_def::input_origin_ is OutputDef.InputOrigin/SetSpot, added to the
    Engine type for this group (the Input-less opaque-span convention of
    Book/Score/ContextDef); upstream's copy constructor copies input_origin_
    and the port's now does the same. Lily_lexer::push_initial_state is
    IParserHost.PushInitialState; add_scope (p->scope_) is
    IParserHost.AddOutputDefScope(def), a distinct member because the port's
    OutputDef scope is a symbol-keyed dictionary rather than a module -- the
    HOST owns routing identifier traffic into the scoped definition, and the
    scripted test host pushes a recorded stand-in module instead. The
    embedded_scm_active alternative's "$1 = o->self_scm ()" replacement swap
    (remove_scope + add_scope) only fires while the body's one-element marker
    list is intact, exactly as upstream's "stupid trick" comment intends.

  EAGER-LOOKAHEAD SITES IN RAG4 (the wave-1 caveat, examined)
  -> RESOLVED by the driver's lazy lookahead (RAG8-RAG10 session): every
     default-reduction site below now reads its following token exactly where
     upstream does. Kept as the record of the divergence the driver change
     closed.

    $@8 (push_note_state) is SAFE: its reduction needs the lookahead upstream
    too -- the output_def_body state must see the next token to choose between
    '}', an assignment, SCM_TOKEN and the music path -- so the first music
    token is lexed in INITIAL mode both upstream and here. The DEFAULT-
    reduction sites do differ: at output_def_head_with_mode_switch
    (push_initial_state) the port lexes the following '{' in the surrounding
    mode where upstream lexes it in INITIAL, and at output_def:
    output_def_body '}' (remove_scope + pop_state) the port lexes the token
    AFTER the '}' in the block's INITIAL mode and scope where upstream lexes
    it in the restored ones; the embedded_scm_active scope swap has the same
    one-token lag. All benign for every parse the ported grammar reaches
    today: '{' lexes identically in all modes, and every current output-def
    context (toplevel, book, bookpart, score) is itself INITIAL-mode with no
    scope-sensitive token adjacent. An output-def ARGUMENT inside a note-mode
    music-function arglist WOULD see the difference -- recorded for the
    RAG8-RAG10 session, alongside the RAG7 caveat this extends.

  music_list / braced_music_list / simultaneous_music   (RAG6)

    reverse_music_list runs with (preserve=true, compress=false) at both list
    sites, over the same ParserActionHelpers.Rag2 implementation RAG2's
    embedded_lilypond uses. music_list error's MY_MAKE_MUSIC ("Music") is
    host.MakeMusic, and the error music is consed UNCONDITIONALLY — upstream
    conses whatever unsmob would say, unlike the music-tested cons of the
    ordinary alternative, and the port does the same.

  music_embedded: duration post_events %prec ':'   (RAG6)

    THE TWIN of RAG2's embedded_lilypond: duration post_events — ported from
    its own body at parser.yy 1522-1533, NOT copied from RAG2: here the
    NoteEvent is ALWAYS made and parser->default_duration_
    (IParserHost.DefaultDuration) is ALWAYS assigned; only the articulations
    are conditional on post events existing. RAG2's side leaves a bare
    duration as a Duration and the default alone. Both files carry
    cross-referencing comments so neither can be "simplified" into the other,
    and RuleActionRag6Tests pins the always-a-NoteEvent behaviour explicitly.

  music_embedded_backup: embedded_scm   (RAG6)

    The group's MYBACKUP site (LYRIC_ELEMENT), over ParserActionHelpers.Rag7's
    MyBackup; in the MYBACKUP branch $$ stays the pre-set $1, which both
    consumers of music_embedded_backup ignore. PER-SITE EAGER-LOOKAHEAD
    ANALYSIS (the RAG7 caveat -> RETIRED with the driver's lazy lookahead;
    the analysis below is the historical record): upstream reaches this reduce
    through a chain of default reductions (SCM_TOKEN -> embedded_scm_bare ->
    embedded_scm -> music_embedded_backup), usually with NO lookahead read;
    the port at the time always read one. Two things could diverge here and
    neither did. (1) The
    pushed-back token's LEX MODE: between this reduce and upstream's next lex,
    the only actions that can run (music_embedded, music_list, lyric_element,
    optional_notemode_duration) contain no lexer push/pop, so the port's
    earlier lex used the same mode upstream's later lex would. (2) The
    action's OWN is_lyric_state observation: the port's scanner changes the
    mode states (notes/lyrics/chords/markup) only from parser actions through
    the host, and the lex-time transient states (Quote, LongComment, Include,
    Version, SourceFile*) are balanced before any token is delivered — so
    lexing the lookahead early cannot flip what the action observes. The same
    reasoning clears pitch_as_music's mode reads, where upstream holds a
    lookahead at reduce time anyway (post_events can only END on one).

  pitch_as_music / make_music_from_simple   (RAG6)

    make_music_from_simple is ported whole into ParserActionHelpers.Rag6.cs
    with its two helpers make_duration and make_chord_elements.
    Lily_lexer::scan_word folds to IParserHost.ScanWord(symbol) returning a
    LexerLookup; is_note/lyric/chord_state are host predicates;
    default_duration_.smobbed_copy () is the boxed DefaultDuration — a fresh
    copy per read, like the smob copies. make_duration's defaulted C++
    parameters (dots = 0, factor = SCM_UNDEFINED) are explicit arguments here;
    RAG16's duration rules are the callers that vary them, and should REUSE
    MakeDuration/MakeChordElements rather than re-adding them.
    make_chord_elements reaches Lily::construct_chord_elements through
    IParserHost.ConstructChordElements (the vendored scm/chord-entry.scm side)
    and stamps each element via MusicObject.SetSpot — a non-music element is
    upstream's null dereference and the port's InvalidCastException: same
    failure, new spelling.

  contexted_basic_music / FINISH_MAKE_SYNTAX   (RAG6)

    The applying half of RAG5's START_MAKE_SYNTAX. FinishMakeSyntax
    (ParserActionHelpers.Rag6) appends the music argument to the prefix list
    with the destructive two-list AppendInPlace exactly as scm_append_x
    re-points the start list's own last pair, then applies through
    IParserHost.ApplySyntax(constructor, location, arguments) — upstream's
    make_syntax (parser, Guile_user::apply, location, scm_car (start), ...).
    The new_lyrics alternative locates the finished context at
    `Input i; i.set_location (@1, @2)` — SourceSpan.Join(@1, @2), NOT @$ —
    while the add_lyrics wrapper gets @$; RuleActionRag6Tests pins the
    distinction.

  partial_function / partial_function_scriptable   (RAG11)

    The Syntax::name sites in these bodies (property_override, property_set,
    repeat, create_script_function) cons the CONSTRUCTOR PROCEDURE without
    calling it -- the same START_MAKE_SYNTAX-shaped seam as RAG5's
    context_prefix -- so they go through IParserHost.SyntaxConstructor with
    the Scheme-side dashed names, verified against the vendored
    ly-syntax-constructors.scm. The call happens later, inside
    partial-music-function's fold (RAG1's identifier_init_nonumber), which
    REVERSES the consed chain: the runtime call list is INNERMOST FIRST, the
    entry that directly receives the supplied argument leading. scm_acons is
    rendered as nested Pair construction at the action sites; no new list
    helper was added. SCM_INUM0, the "no direction" script_dir fallback, is
    exact 0L -- the RAG13 precedent. On a bad property path (SCM_UNBNDP from
    RAG7's grob_prop_path/context_prop_spec) the entry is ly_list (SCM_BOOL_F)
    and, in the tailed alternatives, the inner chain is DROPPED with it,
    exactly as upstream.

    partial_function: script_dir markup_mode markup_partial_function pops the
    markup lexer state MID-ACTION (parser->lexer_->pop_state ()), with the
    partial_markup dispatch before the pop and the partial_text_script
    dispatch after it, in upstream's order. Eager-lookahead note (the wave-1
    caveat): the port lexes the following token BEFORE this reduction, i.e.
    in markup mode, where upstream can pop first and lex after.
    partial_function is consumed ONLY by `identifier_init_nonumber:
    partial_function ETC` (parser.yy 814), and `\etc` lexes to ETC
    identically in markup mode -- the markup Command rule falls back to the
    ordinary escaped-word lookup -- so the two token streams agree on all
    well-formed input; only already-erroneous input could see its error token
    lexed in the markup mode. -> RESOLVED by the driver's lazy lookahead
    (RAG8-RAG10 session): the pop now runs before the following token is
    lexed, exactly as upstream. Nothing to re-examine when RAG15/18/19 land.

  mode_changing_head / mode_changing_head_with_context / mode_changed_music /
  lyric_mode_music   (RAG12)

    The nine mode-keyword heads push lexer states through host members
    (PushLyricState, PushDrumState, PushFiguredBassState, PushChordState beside
    RAG5's PushNoteState), and the CHORDMODE/CHORDS chordmodifier hand-off
    (`chordmodifier_tab_ = Hash_table::alist_to_hashq_table (mods)`) is one
    member, SetChordModifiers -- the alist->hashq-table conversion (vendored in
    scm/lily-library.scm) is folded in because the table's representation
    belongs to the lexer. The MAKE_SYNTAX names (unrelativable-music,
    context-create) are verified against the vendored
    ly-syntax-constructors.scm. The scripted test host RECORDS the pushes
    without switching the scanner; a REAL host must drive ModalScanner's mode
    stack or every mode block lexes in the wrong mode.

    EAGER-LOOKAHEAD CAVEAT, examined for this group per the RAG7 note
    -> RESOLVED by the driver's lazy lookahead (RAG8-RAG10 session), exactly
    the fix this entry asked for. Historical record: upstream reaches every
    head reduction and every pop-site reduction (both mode_changed_music
    alternatives, lyric_mode_music) WITHOUT a lookahead read -- they are
    default-reduction states -- so upstream lexes the token after the mode
    keyword in the NEW mode and the token after the closing brace in the
    RESTORED mode. The port's driver at the time had already lexed both in the
    other mode, and PushBackLookahead could not help: it re-delivers the
    already-FORMED token without re-lexing. Benign for '{', real for e.g. '<<'
    after a mode keyword inside \figuremode, or the first pitch after
    `\lyricmode { .. }`. Only $@10, lyric_mode_music's mid-rule, matched
    upstream: its state can also shift MUSIC_IDENTIFIER, so upstream reads the
    lookahead too -- the grammar's own "We must not have lookahead tokens
    parsed in lyric mode" comment. The driver now defers the read on
    lookahead-free default reductions (Bison's yydefact behaviour), and
    DriverTests pins the mode-head case by name.

  lyric_element_music: lyric_element optional_notemode_duration post_events   (RAG12)

  quotes / erroneous_quotes / octave_check   (RAG16)

  steno_pitch / steno_tonic_pitch / pitch: PITCH_IDENTIFIER quotes   (RAG16)

  from_scm<bool> on exclamations / questions   (RAG16, and RAG14 inherits it)

  IsMusic / IsMusicType / CloneMusic   (RAG15, reused by RAG14)

  post_event_nofinger: script_dir music_function_call   (RAG15)

  the direction guard   (RAG15)

    script_dir's '-' alternative is SCM_UNDEFINED, not zero. Zero would be a
    written "centre"; SCM_UNDEFINED means nothing was written and the engraver
    chooses. Every consumer therefore GUARDS its property write with SCM_UNBNDP
    rather than defaulting -- except '^' fingering / '_' fingering, where the
    direction character IS the rule and upstream writes unconditionally, and
    `post_event: '-' fingering`, which locates the event and writes no
    direction at all. RuleActionRag15Tests pins all four shapes.

  direction_reqd_event: script_abbreviation   (RAG15)

    The shorthand's NAME is a lookup: "Dot" finds \dashDot in scope through

  make_simple_markup   (ParserActionHelpers.Rag15)

    Ported as the identity it is (`return a;`) rather than inlined, because

  script_abbreviation's latin-1 strings   (RAG15)

    scm_from_latin1_string ("Hat") and friends are CLR strings; the alphabet is
    ASCII throughout, and the values exist only to be concatenated after "dash"

  note_chord_element   (RAG14)

    WHERE A CHORD'S DURATION COMES FROM, and worth knowing because nothing else
    in the grammar works this way: the elements inside < > are parsed with NO
    duration, one duration is written after the closing bracket, and this rule
    writes it onto every element. `unsmob<Duration> ($2)->smobbed_copy ()` is a
    re-box of the ported value type -- one box shared by every element, exactly
    as the smob copy is. The post events are appended to the SAME elements list
    rather than to an articulations property, which is what makes `<c e>4->`
    attach to the chord instead of to a note.

    It also completes a path RAG17 could not reach: a figured-bass `<6 4>` goes
    through chord_body's FIGURE_OPEN alternative and then through here, so every
    BassFigureEvent now carries a duration too. A RAG17 real-text test that
    asserted the figure's exact property count was updated (2 -> 3) rather than
    loosened -- the count moving is the rule becoming reachable.

  chord_body: ANGLE_OPEN ...   (RAG14)

    reverse_music_list with preserve = FALSE, compress = FALSE -- unlike RAG6's
    music_list sites, which pass (true, false). Inside < > an unattachable post
    event is DROPPED with a warning rather than kept on an empty chord.

  chord_body_element: music_function_chord_body   (RAG14)

    The unwrapping loop REPLACES $$ as it descends ("$$ = get_property (m,
    "element")"), so a \tweak'd note contributes the NOTE rather than the
    wrapper. A post event passes untouched -- it attaches rather than becoming a
    chord note -- and anything that is neither is the "not a rhythmic event"
    error, whose SCM_UNSPECIFIED chord_body_elements then silently skips.

  make_chord_step   (ParserActionHelpers.Rag14)

    The step is one-based as written and zero-based as a scale index, hence the
    `- 1`; the ported Pitch constructor normalizes its own octave exactly as
    upstream's does (upstream's comment: "Notename/octave are normalized"), so
    step 9 comes out as a second an octave up with no further work. The
    `get_notename () == 6` case is the SEVENTH, flattened because that is what a
    seventh means in chord naming. SHARP_ALTERATION / FLAT_ALTERATION are
    Rational (1, 2) / (-1, 2) inlined at their use sites with the upstream names
    in comments -- the RAG17 precedent.

  chord_items / step_numbers accumulate with $$ rather than $1   (RAG14)

    `$$ = scm_cons ($2, $$)` and `$$ = scm_cons ($3, $$)`: the same value, since
    Bison pre-sets $$ to $1, and ported as values[0] with the difference noted at
    the site so a reader does not go looking for a semantics the port dropped.

  the scripted host's three music shapes   (test infrastructure, RAG14)

    Actions cannot tell the recording MadeMusic, a SyntaxMark standing in for a
    constructor's result, and (under MakeRealMusic) the Engine's real
    MusicObject apart, so the host's music operations handle all three. A
    SyntaxMark now carries properties for one concrete reason: event-chord is
    the one constructor a later rule READS BACK, and the vendored definition is
    (make-music 'EventChord 'elements mlist), so the mark reproduces that one
    property write. Anything else the scripted host is asked for is a loud
    failure rather than a guess.

  A MARKUP IS ITS OWN EXPRESSION   (RAG18/RAG19, the thing to read first)

    Nothing in these two groups interprets markup. `\markup \bold "x"` reduces
    to the LIST (bold-proc "x"), whose head is a procedure fetched out of the
    (lily) module and whose tail is the arguments; it is APPLIED much later,
    when the markup is typeset. That is why so many bodies here are scm_cons
    and ly_list and nothing else, and why a string needs no conversion at all
    to BE a markup.

  IParserHost.LilyImport   (RAG18)

    Lily::line_markup, Lily::score_markup and Lily::score_lines_markup_list are
    (lily) module variables (lily/lily-imports.cc), consed into markup
    expressions WITHOUT being called. This is RAG5's SyntaxConstructor for a
    different module: SyntaxConstructor covers Syntax::, which lives in
    (lily ly-syntax-constructors); LilyImport covers Lily::, which lives in
    (lily). Two members rather than one because they are two modules, and a
    single "look a name up somewhere" member would have hidden that.

  ParseContext.StackLocation   (driver, added with RAG18)

    The companion of RAG3's StackValue, and added for the same reason: a
    mid-rule action reduces as an EMPTY production, so its locations array is
    empty and its @$ is the point-span Bison gives an empty rule -- neither of
    which is @1. markup_scm's mid-rule needs the real @1: it reports "not a
    markup" AT the offending expression and hands the same span to three
    MYBACKUP calls. Driver semantics, not a divergence.

  markup_scm classifies and BACKS UP   (RAG18, $@12)

    The whole rule is its mid-rule action. An embedded #(...) in markup
    position is evaluated, classified, and handed BACK to the token stream as
    the identifier token it turned out to be -- MARKUP_IDENTIFIER or
    MARKUPLIST_IDENTIFIER -- so that the two rules consuming markup_scm can
    tell a markup from a markup list without a lookahead the grammar would
    conflict on. Three details worth keeping: SCM_UNSPECIFIED (an expression
    evaluated for effect) reads as the EMPTY MARKUP LIST rather than as an
    error; anything else is an error that still yields an empty markup so the
    parse continues; and scm_string (SCM_EOL) is the empty CLR string.

  markup_braced_list_body: the cons/splice pair   (RAG18)

    Its two recursive alternatives look alike and do not behave alike. A
    `markup` CONSES on; a `markup_list` SPLICES (Srfi_1::append_reverse, which
    is ParserActionHelpers.AppendReverse, already present). So
    `\markup { a { b c } d }` is a FOUR-element line, not a three-element one
    holding a list. Consing the list instead would produce a different markup
    from the same text with nothing to report it -- pinned by a test.

  markup_top vs markup: identical bodies, different positions   (RAG18)

    `markup_top: markup_head_1_list simple_markup` and
    `markup: markup_head_1_list simple_markup` are the same body verbatim. They
    are separate productions because one may stand at the top of a \markup and
    the other inside a braced list, and the difference is visible only in what
    a command binds to: `\markup \bold a b` bolds through composition at the
    top, while `\markup { \bold a b }` bolds `a` and leaves `b` alone. Both are
    test-pinned at their own position.

  ParserActionHelpers.PrepareMarkupScore   (RAG18)

    \score and \score-lines in markup share nine identical lines -- locate the
    score, and give it a layout if it brought none -- and differ only in the
    markup expression they then build (one wrap for \score, two for
    \score-lines, which yields a markup LIST). Factored, with the divergence
    that od->unprotect () is absent: Boehm-GC bookkeeping, one of the 201
    measured call sites that delete rather than port. get_layout is RAG4's, as
    the wave-2 reuse obligation prescribed.

  the EXPECT_* announcement is the mechanism   (RAG19)

    A markup command's signature is known to the LEXER, not to the grammar. On
    reading \bold the scanner pushes one EXPECT_* token per declared argument
    plus a terminating EXPECT_NO_MORE_ARGS, LAST ARGUMENT ANNOUNCED FIRST
    (ModalScanner.PushMarkupPredicates, ported earlier). So the grammar parses
    commands it has never heard of, and the argument count is right by
    construction. Every RAG19 rule is a consumer of those announcements;
    markup_head_1_item is the shape that leaves the final markup argument
    outstanding for composition to supply, which is what makes `\bold \italic
    "x"` chain without parentheses.

  markup_arglist_partial: discard versus match   (RAG19)

    Six rules, three pairs, and the difference is which announcement they throw
    away. The three recursive ones DISCARD an expectation; the three taking
    markup_command_list_arguments MATCH the first missing argument and keep
    what was written before it. Since announcements arrive last-argument-first,
    the discards are what let `\raise \etc` leave BOTH arguments outstanding
    while `\raise #2 \etc` keeps the 2. All six are exercised from real text.

  the braced markup argument   (RAG19, $@14)

    The one body in these two groups with real logic. Upstream's comment says
    why: an argument expecting neither markup? nor markup-list? may be written
    in braces, and `{ 4 }` or `{ cis }` is ambiguous between a duration/pitch
    and a note event, so both readings are tried -- "a very limited subset of
    the flexible interpretation that music functions do". TWO ORDERING POINTS,
    both load-bearing and neither visible in the result: make_music_from_simple
    must run while the lexer is STILL in note state (upstream says so in the
    comment), which is why the pop is last; and the sticky default duration is
    updated ONLY on the branch that succeeded as music, so a refused `{ 4 }`
    does not silently change what a later bare note means. Both pinned.

  the scripted host reproduces composed-markup-list   (test infrastructure, RAG18)

    A second constructor a later rule reads back, after RAG14's event-chord,
    and read back harder: `markup: markup_head_1_list simple_markup` takes its
    CAR. So the scripted host performs the vendored constructor's list surgery
    for real (a fold of `(append cmd (list prev))`, scm/ly-syntax-constructors
    .scm 241) rather than returning a mark. It is pure consing, needs no
    interpreter, and it lets a markup test assert the composed EXPRESSION --
    which is what the command order actually MEANS -- instead of asserting an
    argument list's order and trusting the constructor.

  the scripted host's IsNoteState follows the scanner   (test infrastructure, RAG18)

    It was a scripted flag, which is fine while a test's text stays in one
    mode. `\markup \score { c }` does not: it is markup, then notes, then
    markup again in one expression, and the note inside it only converts if the
    predicate answers for the MOMENT it is asked. The host now answers from the
    attached scanner's start condition when there is one, and from the flag
    when there is not -- so the earlier groups' tests are untouched.

  markup reachability is fenced separately   (test infrastructure)

    MarkupReachabilityTests runs a corpus through the real scanner and tables
    with every action wrapped in a recorder, and insists all 51 markup actions
    FIRED and no line errored. The rule-action fence proves an action is
    registered and the per-group tests prove the ones they exercise behave;
    neither catches an action that is registered, correct and never reached --
    because its production is unreachable or because the lexer never produces
    the tokens it needs. Half of RAG19 is driven by tokens the scanner invents,
    so that gap was real: the test found four rules the per-group tests had
    missed on its first run, and all four turned out to be reachable.

THE REAL HOST (Session/LilyParserSession.cs) -- added with PHASE 3
-------------------------------------------------------------------------------

  Everything above this line was written against IParserHost/ILexerHost with
  only the tests' ScriptedParserHost behind them. LilyParserSession is the REAL
  one: it answers from a live LilyScheme interpreter and the Engine's types, so
  a .ly FILE can be parsed rather than a token list. Upstream splits it across
  Lily_parser and Lily_lexer; the port keeps them together because the seam the
  actions were written against does not distinguish them.

  THE ly/ INIT LAYER IS NOW VENDORED. 62 files, byte-identical with lily/ly at
  the v2.27.2 pin, embedded beside the scm/ mirror and read through
  LilyPondScheme.ReadInitFile. They are LilyPond SOURCE, not Scheme: the note
  names, the durations, the context definitions, every music function and every
  \override shorthand are ordinary assignments in ordinary .ly files. That is
  why they could not arrive until the last rule action landed -- the init layer
  needs the whole grammar before the first test file needs any of it.

  Divergences, each forced and each recorded on the member:

  LoadInitLayer drives declarations-init.ly, not init.ly

    init.ly's job past the declarations is the SESSION lifecycle -- \maininput,
    the toplevel book handler, the version check -- which the caller owns here.
    The declarations are the part that makes a session able to read music.

  MakeModule is ANONYMOUS again — the named-scope workaround is RETIRED
  (LS-FIX, 2026-08-05)

    THE SHARPEST FINDING OF THE EPG1 SESSION, and it was an expander limitation
    rather than a parser one. LilyScheme's expander resolved an imported MACRO
    only in a module it could name: in an anonymous module that merely USES
    (lily), `define-music-function` read as an ordinary variable, so its
    argument list was EVALUATED and every music function in
    ly/music-functions-init.ly failed with an unbound variable named after its
    first parameter. Isolated to a two-line reproduction -- the same form
    expands in a named module and fails in an anonymous one. The port named its
    parser scopes (lily parser-scope N) from EPG1 until 2026-08-05 to get
    correct expansion.

    THE REAL MECHANISM, found when the fix landed in LilyScheme: psyntax
    round-trips module identity BY NAME (hygiene wraps carry the module name
    and resolve it back through the registry), and Guile squares that with
    anonymous modules by having module-name INVENT a name on first ask and
    register the module under it -- boot-9's own behaviour. LilyScheme's
    module-name now does exactly that (SchemeModule.EnsureName, fenced by
    AnonymousModuleMacroTests), so parser scopes, \header blocks and output
    definition scopes are all anonymous again, matching upstream's
    ly_make_module. The workaround's registration half is gone from
    Engine/Bootstrap/LilyModules.cs the same day.

  set_spot takes an INPUT, never a raw span (fixed 2026-08-05)

    The session's SetSpot paths (MakeMusic, SetMusicSpot, LocOnCopy, and
    Rag18's markup-score helper) stamped the parser's SourceSpan struct
    straight into 'origin. Upstream's set_spot takes an Input, and nothing
    failed until the batch runner's first sweep ran an ly:input-location?
    type check over a music 'origin and answered #f on every note the parser
    had built -- the silent-defect shape exactly: two representations that
    print alike, told apart only by the first real consumer. All spot paths
    now convert through SchemeLocation; the scripted test host stamps the raw
    span (it has no Sources to build an Input from) and says so.

  Embedded Scheme is evaluated THROUGH THE EXPANDER

    EvalSchemeToken uses TreeIlEvaluator.ExpandAndEval over
    CurriedDefinitions.Expand, not the bare evaluator. Almost everything a .ly
    file embeds is a macro use; evaluated without expansion each one dies on an
    unbound variable named after its first argument. The evaluation happens in
    the innermost SCOPE with the interpreter's current module pointed at it,
    which is Lily_lexer::set_current_scope.

  The initial scope is a fresh module, not (lily)

    Lily_lexer's constructor is `add_scope (ly_make_module ())`, and
    lookup_identifier_symbol is module-LOCAL per scope. Opening on (lily)
    instead puts every `#(define ...)` where the local lookup does not look --
    output-def-music-handler then reads as unbound at the first \layout.

  ParseEmbeddedScheme reads a SUFFIX

    Upstream hands the input port to Guile's reader, which leaves it positioned
    after the datum. LilyScheme's reader starts at 0, so the port reads
    input.Substring(position) and reports how much it used. Same answer; the
    only visible difference is that a datum's recorded column is relative to
    the expression rather than to the line.

  Score and Book are copied member-by-member

    Upstream clones them with copy constructors the Engine types do not have
    yet -- the first-light path never needed one. The copies are SHALLOW over
    music, header and the score/bookpart lists, which is what upstream's are.

  od->unprotect () and friends are absent

    Boehm-GC bookkeeping, among the 201 measured call sites that delete rather
    than port under .NET's precise collector.

THE SCANNER'S INCLUDE STACK (added with PHASE 3)
-------------------------------------------------------------------------------

  ModalScanner now owns an input stack: \include pushes the current text,
  file name and position and switches; end of input pops back. This is
  upstream's Includable_lexer, and the important part is what is NOT stacked --
  the MODE stack is shared, so an included file inherits the mode it was
  included from. That is what lets the ly/ init files be \include'd from
  inside a \layout.

  The include is opened between tokens in Next() rather than inside the rule
  action, so the rule stays a translation of lexer.ll's action. Resolution goes
  through IncludeResolver: the vendored ly/ layer first, then the caller's
  IncludePath. An unresolved include is a LEXER ERROR, never a silent skip -- a
  skipped include produces a file that parses and means something else.

NAMING
-------------------------------------------------------------------------------

  The rule-action partial-class files are named by RULE ACTION GROUP
  (LilyPondRuleActions.Rag1.cs, .Rag13.cs, ...) -- the session-sized, disjoint
  groups the porting effort is planned and fenced by. The group's grammar

  CompletedGroups theory is the ledger of which groups are done.

CORRECTIONS MADE 2026-08-04 (EPG1) -- FOUR CLAIMS ABOVE THAT WERE WRONG
-------------------------------------------------------------------------------

  Each of these was recorded here as a deliberate divergence, and each was
  disproven the first time the ly/ init layer was actually driven end to end.
  They are kept, with the reasoning, because the SHAPE of the mistake repeats:
  a claim that a difference is invisible, made while the only thing exercising
  the code was a scripted host.

  1. "strings -> CLR string as produced by the lexer; MutableString is accepted
     wherever a value is TESTED for stringness."

     It is accepted wherever the PORT tests for stringness, and nowhere else.
     CodeBrix.LilyScheme's `string?` is `value is MutableString`, so a CLR
     string is not a Scheme string at all -- `markup?`, `markup-list?` and
     everything built on them answer #f for one. `\markup { \italic "cresc." }`
     therefore handed composed-markup-list a list whose element was not a
     markup, and the init layer died inside a markup constructor, nowhere near
     the lexer.

     Now: every token value upstream builds with `to_scm (str)` is built with
     ModalScanner.SchemeText, which is a MutableString. Tests that assert what
     a token SAYS go through SchemeTextAssertions.AsText, because MutableString
     is mutable and compares by identity.

  2. MAKE_SYNTAX passed the location as the constructor's FIRST ARGUMENT.

     It does not. parser.yy's make_syntax calls with_location, which is
     `ly_with_fluid (Lily::f_location, loc, [] { scm_call_n (proc, ...); })` --
     the location is bound to the %location fluid for the dynamic extent of the
     call and read back as (*location*). Not one constructor in
     scm/ly-syntax-constructors.scm declares a location parameter, so every
     MAKE_SYNTAX in the port was calling with one argument too many.

     Now: LilyParserSession.WithLocation binds the fluid; MakeSyntax and
     ApplySyntax pass only the real arguments.

  3. Locations were the port's own SourceSpan, boxed.

     Upstream every location IS an Input: ly:input-location? answers on it,
     ly:input-file-line-char-column reads it, Input::warning quotes the line it
     points at, and ly:set-origin! type-checks it. SourceSpan now carries
     character offsets, the session keeps a SourceFile per opened input, and
     SchemeLocation builds a real Input. A span with no offsets -- one built by
     hand in a fixture -- becomes an Input with no source file, which reports
     "position unknown" rather than a plausible wrong place.

  4. LookupIdentifier searched each scope's OWN bindings.

     Lily_lexer::lookup_identifier_symbol uses scm_module_variable, which
     searches the module AND WHAT IT IMPORTS. Since every parser scope uses
     (lily), the local-only search hid the entire Scheme layer.

  Two more of the same class, found the same way:

  * ILexerHost.LookupMarkupCommand looked up the BARE word. Upstream's
    lookup-markup-command looks up `<word>-markup`, falling back to
    `<word>-markup-list` -- the suffix is what define-markup-command binds --
    and it looks it up in the current module, not scope-locally. Every markup
    command in the vendored layer read as an unknown command.

  * push_markup_predicates puts THE PREDICATE on an EXPECT_SCM, because the
    grammar's arglist rules call it. The port carried the NAME the token choice
    was made from, so the first arglist rule to test an argument tried to call
    a string. MarkupPredicate now carries both.

  All six were invisible to the 520 tests here because the rule-action and
  markup-reachability suites drive a ScriptedParserHost, which is honest about
  being scripted -- it answers from tables, so nothing it does can disagree
  with the Scheme layer. REGISTERED, BEHAVING and REACHABLE are three different
  things, and a scripted host can only ever prove the first two.

THE ly:parser-* SURFACE (EPG1)
-------------------------------------------------------------------------------

  lily-parser-scheme.cc's bindings live in the ENGINE
  (Bootstrap/ParserPrimitives.cs), over the Origins/ILilyParser seam, because
  CodeBrix.LilyPort.Parsing references the Engine and not the other way round.
  LilyParserSession implements the seam (Session/LilyParserSession.Parser.cs).

  The current parser is the %parser fluid scm/lily.scm defines, exactly as
  upstream -- LilyParserSession.AsCurrentParser publishes itself into it for
  the duration of a parse and restores what was there before. Upstream sets it
  once per run; the port scopes it, because several sessions can exist in one
  process and the innermost is the one those bindings mean.

  ly:parser-set-note-names diverges from a LITERAL reading of upstream, and
  must. Upstream's body only acts when the lexer is in note state -- but the
  assignment inside it is `Lily::pitchnames = names`, a handle onto (lily)'s
  own variable, so the table is stored regardless and the pop/push only makes
  an ALREADY-OPEN note mode pick it up. declarations-init.ly calls
  note-names-language at top level, outside any note mode; a port that only
  acted inside note state stored nothing, and every note name in the init layer
  read as "not a note name".

  STILL OWED by this file: ly:parse-file and ly:parse-init. Both open a file,
  build a Sources and a parser, and drive the whole thing -- which is EPG3's
  internal batch runner, not a binding.

EMBEDDED SCHEME -- parse-scm.cc COMPLETE (EPG1, 2026-08-04)
-------------------------------------------------------------------------------

  The reader half is LilyParserSession.ParseEmbeddedScheme; the evaluation half
  is LilyParserSession.EvalScheme, which is Lily_lexer::eval_scm including its
  extra-token discriminator. Both scm_c_catch handlers are ported.

  THE CATCH IS THE POINT OF THE FILE. An expression the reader or the evaluator
  cannot make sense of becomes a LOCATED non-fatal diagnostic and the parse
  continues; before it, one bad #(...) took the run down with a CLR exception
  and everything after it in the file was invisible. That is what turned the
  ly/ init layer from "it fails" into a per-file, per-line worklist.

  On a reader failure the port consumes ZERO characters, and that is upstream's
  behaviour rather than an approximation: Parse_start::parsed_ is only .set()
  on the success path, so after a throw it is a default-constructed Input,
  parsed.size() is 0, and skip_chars(0) leaves the scan position just past the
  `#'. The text is then re-scanned as ordinary LilyPond. Consuming to the
  reader's stopping point instead would eat the rest of the file, because an
  unterminated list runs to end of input.

  `$' is EVALUATED BY THE LEXER and its token comes from the value's type
  (scan_scm_id), which is why $foo stands in for a music expression, a pitch, a
  duration or a music function wherever the corresponding *_IDENTIFIER is
  legal. A failed evaluation produces NO TOKEN AT ALL -- upstream's rule ends in
  `if (!scm_is_eq (yylval, SCM_UNSPECIFIED)) return token;' and otherwise falls
  off the end of the action, which in flex means "text consumed, keep
  scanning". Inventing a token there would report one mistake twice.

  The CLOSURES alist is keyed by the offset of the character after the `#' or
  `$', matching EmbeddedLilyReader's `offset = lily.Length'. Consulted only
  while reading the top input (lexer_->top_input(), i.e. include depth < 2),
  because an \include'd file's offsets have nothing to do with the clone's.

  DELIBERATE DIVERGENCES, both recorded rather than fixed:
    * No -dcompile-scheme-code path. LilyScheme has no byte-compiler, and the
      option is off by default upstream for its own reasons (a byte-compiler
      limitation above a few thousand expressions).
    * No scm_display_backtrace under -ddebug-eval. The located diagnostic plus
      the interpreter's own message is what the port reports.

THE LEXER'S BASE MODE IS `notes' (EPG1, 2026-08-04)
-------------------------------------------------------------------------------

  Lily_lexer's constructor ends in push_note_state() -- lily-lexer.cc 129, and
  again at 154 for the clone constructor. A lexer is therefore in NOTE MODE
  from its first character, and nothing in the grammar ever pops down to
  INITIAL. LilyParserSession.ParseText pushes it, and pops on the way out.

  This is why

      ignatzekExceptionMusic = { <c e gis>-\markup { "+" } }

  reads as pitches at the top level of chord-modifiers-init.ly with no
  \notemode anywhere: there is no mode change, the file simply never left note
  mode. A port whose base was INITIAL lexed every one of those as a bare
  SYMBOL, and the diagnostic named the note name rather than the mode.

  Related, and found with it: a character terminal's NAME is the character
  literal exactly as the grammar's text spells it, so `'` is the terminal
  '\'' and not '''. ModalScanner.CharacterTerminalName does the escaping.
  Getting it wrong is silent -- Terminal() answers -1 for an unknown name and
  the driver reports "unexpected token -1" at what looks like an ordinary
  syntax error. The octave mark accounted for 25 init-layer errors.

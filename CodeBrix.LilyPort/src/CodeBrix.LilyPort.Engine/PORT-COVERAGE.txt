PORT-COVERAGE -- CodeBrix.LilyPort.Engine
=========================================

Deliberate divergences from LilyPond's lily/ sources, with the reason. Read this
before assuming any file here is a literal translation.

Started 2026-08-03, at the beginning of the Milestone 6 Phase 1 work.


-------------------------------------------------------------------------------
VALUE-TYPE SEMANTICS
-------------------------------------------------------------------------------

  lily/stencil.cc, lily/include/stencil.hh  ->  Layout/Stencil.cs

    Stencil is a mutable STRUCT, not a class.

    Upstream's Stencil is a class held and copied BY VALUE: `Stencil toadd (s);`
    appears all through stencil.cc, and stencil.hh states outright that C++ code
    must not modify a Stencil shared with Scheme (it deletes the non-const
    unsmob<Stencil> to enforce it). A C# class would have silently turned every
    one of those copies into an alias, and add_at_edge / stack would then have
    mutated their argument.

    Stencil also carries a private _initialized flag. C# cannot intercept
    `default(T)`, and a default-constructed Stencil must read back as EMPTY
    extents rather than as a zero-size stencil at the origin. This is the same
    device Interval and Rational already use in Flower, for the same reason.

  lily/spring.cc, lily/include/spring.hh  ->  Layout/Spring.cs

    Spring carries the same _initialized flag. Upstream's default constructor
    sets every field to 1.0, not 0.0, so a zeroed Spring would be a zero-length
    spring of zero strength -- which the line spacer would then divide by.

    Spring::operator*= became Spring.ScaleBy plus an `operator *`, because C#
    compound assignment cannot be defined directly.

  lily/box.cc  ->  Layout/Box.cs

    Box.IsEmptyOn(Axis) tests for the empty SENTINEL VALUES, not for
    Interval.IsEmpty. Upstream's Box::is_empty(Axis) compares the bounds against
    a default-constructed Interval bound for bound, so an inverted-but-finite
    interval (left > right, both finite) is NOT empty by this test even though
    Interval::is_empty() calls it empty. Skyline construction depends on the
    distinction. There is a test for it.


-------------------------------------------------------------------------------
NAMING
-------------------------------------------------------------------------------

  lily/music.cc  ->  Music/MusicObject.cs

    class Music -> MusicObject. The containing namespace is already
    CodeBrix.LilyPort.Engine.Music; a type with the same name as its namespace
    is legal C# but forces every reference to be fully qualified.

  lily/system.cc  ->  Objects/SystemGrob.cs

    class System -> SystemGrob, and this one is not cosmetic. A class named
    `System` in a namespace shadows the ROOT NAMESPACE for every file beside
    it, so System.Math, System.Collections and System.Numerics all stop
    resolving -- in files that never mention the type. It broke Grob.cs and
    Prob.cs the moment the file was added.

  lily/translator.cc Translator::finalize  ->  Translator.FinalizeTranslation
  lily/translator-group.cc likewise

    `Finalize` in C# is object.Finalize -- the destructor. Overriding it would
    have handed the method to the garbage collector instead of to the timestep
    protocol, and the compiler warns (CS0465) rather than errors, so it would
    have compiled and silently never run.


-------------------------------------------------------------------------------
ALGORITHMIC EQUIVALENTS
-------------------------------------------------------------------------------

  lily/skyline.cc internal_build_skyline  ->  Layout/Skyline.cs

    Buildings are sorted with a hand-written STABLE MERGE SORT rather than
    List<T>.Sort. This is the same problem the Scheme `sort` primitive already
    hit: upstream's LessThanBuilding is not a strict weak ordering once heights
    tie on infinity, and .NET's introsort VALIDATES its comparer and throws
    "IComparer.Compare() returns inconsistent results" where the C++ simply
    carries on. A merge sort asks only "does b precede a", so it copes.

    The same applies to SimpleSpacer.CompressLine's spring ordering, where
    upstream uses std::sort (unspecified tie order); the port's stable sort
    makes a run reproducible and is equivalent to the algorithm either way.

  lily/skyline.cc internal_merge_skyline  ->  Layout/Skyline.cs

    Upstream walks two iterators and swaps BOTH the iterators and the containers
    they point into. The port keeps an index plus a list reference per side and
    swaps the pairs together. Same walk; C# has no iterator that can be
    reseated across containers.

  lily/lookup.cc polygon point lists  ->  Layout/Lookup.cs

    Upstream conses each vertex onto the FRONT of the coordinate list, so the
    emitted point order is the reverse of the order the vertices are visited.
    Preserved exactly, because the regression comparator diffs output text. For
    a closed polygon this only changes the winding, which is why upstream can
    do it without visible consequence.

  Translator listener registration

    Translator.ListenTo. Same set of listeners, reached by a route C# can

  Prob::transpose's pitch-alist branch

    CLOSED 2026-08-08 (carry-forward session). The identity stand-in this entry
    recorded outlived its reason: the real algorithm landed with EPG19 as
    MusicSequence.TransposeKeyAlist and nothing re-pointed this branch at it, so
    every `\key PITCH \SCALE' carried the UNTRANSPOSED scale pattern — visible

    flats), because the layout comparator does not grade key signatures by
    count. The branch now calls the real algorithm, whose output was ALSO
    corrected to carry SCHEME numbers: upstream answers
    to_scm (orig.get_alteration ()), and the Flower Rational the port stored
    read identically from C# and threw wrong-type-arg the moment Scheme's
    alterations-in-key multiplied it. CarryForwardFixTests fences both, with
    the d-minor expectation hand-computed. The stale-stand-in lesson is
    RATCHET-FIX's, again: a recorded absence stops being true the moment its
    owner lands, and nothing re-checks it.

UPSTREAM BEHAVIOUR THAT LOOKS LIKE A BUG BUT IS NOT
-------------------------------------------------------------------------------

  ly:camel-case->lisp-identifier's DOCSTRING IS WRONG.

    general-scheme.cc:352 claims FooBar_Bla -> foo-bar-bla. lily/misc.cc:59-77
    inserts a hyphen before each capital AND separately replaces underscores
    with hyphens, so the real answer is foo-bar--bla, with two. Ported
    faithfully; the test says so.

  from_scm<bool> IS NOT SCHEME TRUTHINESS.

    lily-guile.hh:468-479 -- with its default fallback it is
    scm_is_eq (s, SCM_BOOL_T): ONLY #t is true. An unset property reads back as
    the empty list, which Scheme itself would call TRUE. Ported as
    SchemeUtilities.ToBool. SchemeUtilities.IsSchemeTrue is the other one, for
    the places upstream really does call scm_is_true. Getting these the wrong
    way round inverts every "does this grob have this flag" test in the engine.

  Grob::is_live() is scm_is_pair(immutable_property_alist_).

    grob-property.cc:322-325. A grob built with an EMPTY immutable alist is dead
    on arrival, and SetProperty/SetObject then silently do nothing. Real grobs
    always carry a `meta` entry so this never bites upstream, but a test fixture
    that builds a grob from '() will look like a property-storage bug.

  Skyline::raise moves the outline in +y REGARDLESS of direction.

    The stored intercept is signed by the direction on the way in and read back
    signed by it again, so the two signs cancel. That is what lets a whole
    Skyline_pair be moved without distorting it.

  Skyline::height at a shared building edge returns the LEFT building's height.

    std::lower_bound finds the first building whose right edge reaches x, so a
    point exactly on a boundary belongs to the building that ENDS there.

ADDED 2026-08-03 (second pass) -- the column and system layer
-------------------------------------------------------------------------------

  lily/grob-array.cc, lily/pointer-group-interface.cc  ->  Objects/GrobArray.cs

    Grob_array privately inherits std::vector<Grob*> upstream and re-exports a
    chosen subset; the port composes a List<Grob> and exposes the same subset,
    because C# has no private inheritance.

    Grob_array::remove_duplicates sorts by ADDRESS and uniquifies. The port
    keeps first-occurrence order instead. That is a superset of what the
    callers need (they only care that duplicates are gone) and it is
    deterministic, where sorting by address is not.

    PointerGroupInterface.ExtractGrobSet does NOT create the array, matching
    upstream's extract_grob_set. Only GetGrobArray creates. Reading a link that
    most grobs never have must not install an empty array on every one of them.

  lily/paper-column.cc  ->  Objects/PaperColumn.cs

    Paper_column::rank_ is vsize (unsigned) upstream and starts at VPOS, the
    unsigned sentinel. The port uses int with InvalidRank = -1, because the
    rank is compared and decremented in signed arithmetic all through the
    spacing code and an unsigned sentinel there is a trap.

    NOT ported: print, before_line_breaking, break_align_width,
    get_interface_extent, is_extraneous_column_from_ligature. All need
    Break_alignment_interface or Separation_item.

    Paper_column::minimum_distance omits the Separation_item::conditional_skyline
    merge, which needs Separation_item. The skyline half is exact.

  lily/system.cc  ->  Objects/SystemGrob.cs

    Ported: the element and column registries, typeset_grob, add_column,
    column, used_columns_in_range, broken_col_range, element_count,
    spanner_count, pre_processing, post_processing, and the paper-column-only
    bound rule.

    System::pre_processing's loop is bounded by the ORIGINAL element count on
    purpose: breaking appends the clones to the same array and the clones must
    not be broken in turn. Preserved exactly.

  lily/spaceable-grob.cc  ->  Objects/SpaceableGrob.cs

    Whole file except the ADD_INTERFACE declaration.

  lily/simple-spacer.cc get_line_forces / get_line_configuration
                                              ->  Layout/LineSpacing.cs

    Split into its own file rather than appended to SimpleSpacer.cs: these read
    the SCORE (columns, springs, rods, break permissions) while SimpleSpacer.cs
    is pure arithmetic, and keeping the seam visible is worth one extra file.

    get_column_description's rod-target lookup uses std::lower_bound over the
    rank-ordered column list and then checks the ranks match. The port scans
    forward comparing ranks, which gives the same answer without requiring the
    list to be a random-access range over the very same objects.

    Column_x_positions is in SimpleSpacer.cs (it is three fields and upstream's
    own .cc is 26 lines).

  lily/prob-scheme.cc  ->  Bootstrap/ProbPrimitives.cs

    ly:make-prob, ly:prob-mutable-properties, ly:prob-immutable-properties.

    ly:module->alist dumps a module's bound variables as an alist, skipping
    unbound variables the way upstream does (without upstream's programming

    not an inconsistency).

  lily/function-documentation.cc  ->  GeneralPrimitives.cs   DIVERGENCE

    ly:get-all-function-documentation returns an EMPTY hash table. Upstream

    §7b blocker). DIVERGENCE, minor: the table is rebuilt per call from the
    C# registry, where upstream hands out its one live table. Interfaces are
    all registered at startup, so the difference is unobservable today.

ADDED 2026-08-03 (fifth pass) -- Track T: iterators, the override chain, engravers
-------------------------------------------------------------------------------

  lily/music-iterator.cc         ->  Translation/MusicIterator.cs
  lily/simple-music-iterator.hh      (MusicIterator, SimpleMusicIterator,
  lily/event-iterator.cc             EventIterator)
  lily/sequential-iterator.cc    ->  Translation/SequentialIterator.cs
  lily/music-wrapper-iterator.cc     (CalculatedSequentialMusic,
  lily/simultaneous-music-iterator.cc MusicWrapperIterator, SequentialIterator,
  lily/event-chord-iterator.cc       SimultaneousMusicIterator,
  lily/rhythmic-music-iterator.cc    EventChordIterator, RhythmicMusicIterator)
  lily/global-context.cc         ->  Translation/GlobalContext.cs
  lily/nested-property.cc        ->  Objects/NestedProperty.cs
  lily/context-property.cc       ->  Objects/GrobProperties.cs
  lily/staff-symbol-engraver.cc  ->  Translation/FirstEngravers.cs
  lily/clef-engraver.cc              (StaffSymbolEngraver, ClefEngraver,
  lily/note-heads-engraver.cc         NoteHeadsEngraver, AxisGroupEngraver)
  lily/axis-group-engraver.cc

  FIVE DEFECTS THIS WORK UNCOVERED, each of which was silent:

  1. THE SETTER HALF OF LY_DEFINE_WITH_SETTER WAS NEVER WIRED.
     The macro does two things: define the getter as a primitive, AND bind the
     Scheme name to scm_make_procedure_with_setter (getter, setter). The port
     did only the first. Reading a property worked perfectly; the failure was
     confined to generalized set! -- (set! (ly:music-property m 'duration) d)
     -- which is exactly the form make-music uses, so NO music could be built
     by LilyPond's own Scheme while every read-only test passed.
     Fixed in Bootstrap/SetterBindings.cs, which must run LAST in
     CreateInterpreter because it looks both halves up by name.
     This is the same extraction gap that hid these six entry points from
     entry-points.tsv in the first place; the tsv was corrected in the §7b
     pass, the SETTER behaviour had still never been.

  2. TYPE PREDICATES FOR PORTED TYPES STILL ANSWERED #f.
     InstallStubs answers #f for a type predicate, and that is CORRECT while
     the type is unported -- no instance can exist. The moment the type IS
     ported the same stub is actively wrong: ly:duration? said a real Duration
     was not one, and the symptom was "Type check for `duration' failed",
     naming the property rather than the predicate. 16 predicates were in this
     state. Bootstrap/TypePredicates.cs implements them and NAMES the ones
     still legitimately unported, so the fence test can insist every declared
     predicate is in one list or the other. PORTING A TYPE NOW CARRIES AN
     OBLIGATION TO REGISTER ITS PREDICATE THERE.

  3. THE MUSIC-SEQUENCE CALLBACKS WERE PORTED BUT NEVER REGISTERED.
     MusicSequence already had CumulativeLength, FirstStart and the rest.
     define-music-types.scm reaches them BY NAME through length-callback and
     start-callback properties, so an unregistered callback left sequential
     music reporting zero length -- which makes the interpretation loop decide
     there is no music and stop, silently producing an empty score.

  4. Context.NowMoment WAS PER-CONTEXT. Upstream's Context::now_mom walks to
     the TOP context and returns its moment; only Global_context stores one.
     A per-context clock leaves every engraver below the root reading zero
     forever, and reading the wrong moment is not an error anywhere -- it just
     puts every grob at the wrong time.

  5. Context.IsBottomContext ALSO REQUIRED NO CHILDREN. Upstream's test is
     purely !acceptance_.has_default (). The extra condition made a context
     that accepts nothing but has a child look non-bottom, so the iterators'
     descend_to_bottom_context would try to create one level too many. The
     fixture in TranslationTests that covered this had never expressed
     acceptance at all, and had been passing on the wrong implementation.

  DIVERGENCES, all deliberate:

  * CONTEXT CREATION IS FACTORY-DRIVEN. Upstream's core_find builds a path of
    Context_defs (from the output definition) and creates the whole hierarchy
    at once, so it knows an unbuilt type's acceptance list in advance. Those
    definitions come from ly/engraver-init.ly and therefore arrive with the
    PARSER (Track P). Until then Context.ContextFactory is the seam: the
    caller supplies how a named type is built, and PathToAcceptableContext
    descends ONE level at a time, recursing once the child exists and its own
    acceptance list is readable. The search/create logic (Find, UncheckedFind,
    CoreFind, and the CREATE_ONLY / FIND_CREATE modes) is upstream's shape.

  * Engraver.LookupGrobDefinition falls back to all-grob-descriptions when the
    context tree carries no Grob_properties at all. Upstream always has a
    Global context holding the defaults, so it never needs the fallback; the
    port has it so an engraver can be exercised on a hand-built tree.

  * ClefEngraver.ProcessMusic omits upstream's break_allowed (context ())
    guard, which limits clef creation to points where a break has not been
    forbidden. That needs the break machinery, which is deliberately later
    work. The effect is that a clef may be created where upstream would not
    have bothered, never that one is missing.

  * StaffSymbolEngraver omits the staff-span listener (Unique_span_event_
    listener), so the staff symbol always opens at the first timestep and
    closes at the end rather than responding to \startStaff / \stopStaff.
    The span-event listener family is not ported yet.

  * AxisGroupEngraver omits the hara-kiri "interesting item" bookkeeping,
    which needs Hara_kiri_group_spanner.

  * NOT PORTED, and recorded in IteratorPrimitives.NotYetPorted: 20 of the 28
    iterator constructors upstream declares -- repeats, volta brackets,
    property push/pop, grace, tuplets, part combining, lyric alignment,
    context changes, quoting. Their stubs stay in place ON PURPOSE, so a music
    type that needs one is REPORTED as new demand rather than being silently
    handed a default iterator that would drop its meaning.

ADDED 2026-08-03 (fourth pass) -- the C++ ADD_INTERFACE table (plan O8, option C)
-------------------------------------------------------------------------------

  lily/*.cc ADD_INTERFACE macros  ->  Scheme/grob-interfaces.tsv
                                      Bootstrap/GrobInterfaceTable.cs

    Upstream declares grob interfaces from TWO places, and the port needs both:

      86 in C++, via ADD_INTERFACE (cl, description, properties) across 77
         lily/*.cc files. The macro expands to a static Grob_interface<cl>
         object whose constructor registers an init function, so all 86 are in
         the interface hash table BEFORE any Scheme runs.
      88 in Scheme, via ly:add-interface in scm/define-grob-interfaces.scm,
         added while the Scheme layer loads.

    Two interfaces are declared in BOTH halves -- clef-modifier-interface and
    percent-repeat-interface. Upstream's ordering means the Scheme declaration
    wins, because it runs later and internal_add_interface does a hashq_set_x
    overwrite. The port reproduces that outcome by construction rather than by
    special case: GrobInterfaceTable.Register runs inside RegistryPrimitives
    .Install, which is before the Scheme layer loads.

    NAME DERIVATION, ported exactly, because getting it wrong is silent:
    lily/grob-interface.cc add_interface takes the C++ CLASS name, applies
    camel_case_to_lisp_identifier (lily/misc.cc: lowercase the first character,
    prefix '-' before every subsequent uppercase one, then replace '_' with
    '-'), and appends "-interface" ONLY IF that is not already the suffix.
    So Accidental_interface -> accidental-interface (not
    accidental-interface-interface), while Accidental_placement ->
    accidental-placement-interface. Property lists are whitespace-split, as
    parse_symbol_list (lily/lily-guile.cc) does.

    WHY A DATA TABLE AND NOT PER-CLASS DECLARATIONS (the O8 decision): the
    classes those 86 macros name are mostly not ported yet, so waiting for them
    would leave the interface table incomplete for as long as the port takes --
    and document-backend.scm, which reads it, would stay blocked. Extracting up
    front completes the table immediately.

    THE ASSERT-ON-PORT RIDER, which is the other half of the decision: a grob
    class, as it gets ported, does NOT re-declare its interfaces. It ASSERTS
    them against this table (GrobInterfaceTable.CheckPortedGrob, exercised from
    the class's tests). Re-declaration would let the two copies drift silently;
    an assertion turns drift into a test failure -- including on any future
    re-sync to a newer LilyPond, where the extraction is re-run and any changed
    property set breaks the assertion rather than being absorbed.

    MEASURED EFFECT: document-backend.scm now LOADS. It was the last §7b file
    blocked on engine breadth rather than on the parser; the on-demand set went
    from 34 of 37 to 35 of 37 (89 of 91 overall).

-------------------------------------------------------------------------------
THE ON-DEMAND LOAD FENCE (P7), AND A SECOND FIXTURE TRAP
-------------------------------------------------------------------------------

  tests/.../LilyPondOnDemandLoadTests.cs fences the 37 vendored scm/ files
  LilyPond loads ON DEMAND, the way LilyPondSchemeLoadTests fences the 54 it
  loads at startup. Together they account for all 91.

  Two design points that are deliberate, not incidental:

  1. Counts are asserted with EQUALITY and the non-loading files are named
     INDIVIDUALLY with the unported piece each waits on. A floor would let an
     unblocked file be absorbed silently; the point of the fence is that engine
     or parser work which unblocks one of them BREAKS the test and forces the
     milestone-6 exit checklist to be consulted.

     This is not theoretical -- it fired within the hour. The fence was written
     against 34 of 37 with document-backend on the blocked list; the O8 work
     immediately below unblocked that file, the fence failed, and the recorded
     state was updated to 35 of 37 with document-backend moved to the list of
     files whose loading is asserted. Two remain, both parser-gated:
     hyphenate-internal-words and documentation-generate.

  2. The on-demand set is defined by SUBTRACTION -- every vendored file the
     startup pass did not load -- not as "the files not in load-order.txt".
     lily.scm is not in its own load list because it DRIVES that list, yet it
     is loaded at startup. Defining the set the other way attempts it twice
     and collects a correct ly:error about redefining default-global-scale as
     if it were a failure.

  THE TRAP: LoadViaLilyScm installs its primitive-load-path hook with the
  startup LoadReport CAPTURED IN THE CLOSURE, and leaves it installed. Any
  on-demand file that ly:loads another file therefore APPENDS to the startup
  report afterwards -- documentation-generate alone pulls in the whole doc
  pipeline. Reading startup.Loaded.Count after the on-demand pass reports 71,
  not 54, and the "of 91" arithmetic built on it is meaningless. The count and
  the name set must be SNAPSHOTTED before the on-demand pass begins. This cost
  a measurement before it was understood; the fence snapshots, and comments
  why at the point of the snapshot.

-------------------------------------------------------------------------------
A TEST-FIXTURE TRAP WORTH KNOWING
-------------------------------------------------------------------------------

  get_line_forces uses `end_spring_` for the LAST spring of every candidate
  line, and get_column_description only records end_spring_ when the FOLLOWING
  column has a LEFT prebroken piece. A line STARTER is likewise the right
  prebroken piece, not the original column.

  So a fixture of plain, un-prebroken columns silently falls back to a DEFAULT
  spring for every candidate line, and every force comes out wrong in a way
  that looks like a solver bug. The real pipeline never sees this because
  System::pre_processing prebreaks first. Test fixtures must prebreak too, and
  must register springs from the prebroken pieces as well as the originals.

  -> Since later on 2026-08-03 the trap is GUARDED rather than merely
  documented, in two places:

  1. Engine side: both LineSpacing entry points now check for the state that
     System::pre_processing makes impossible in the real pipeline — a column
     that can begin or end a line but has never been prebroken — and report a
     programming error naming the column ranks
     (LineSpacing.WarnAboutUnbrokenBreakColumns). This check is NEW-IN-PORT
     and DIAGNOSTIC ONLY: upstream has no equivalent because it never needs
     one, and the computed results are unchanged — only the silence is gone.

     A related leniency, also deliberate and previously unrecorded: upstream
     get_line_configuration dereferences find_prebroken_piece (RIGHT/LEFT) on
     its two boundary columns UNCHECKED, so an un-prebroken boundary column
     would crash it. The port (PrebrokenOr) substitutes the original column
     instead, so a fixture still gets a best-effort answer — after the
     programming error above has named the real problem.

  2. Fixture side: tests/CodeBrix.LilyPort.Engine.Tests/SpacingFixtures.cs is
     the canonical way to build spacing fixtures. PrebrokenChain prebreaks
     through the REAL SystemGrob.PreProcessing and registers every spring on
     the prebroken pieces as well as the originals (RegisterSpring);
     PlainChain is for spring/rod accounting tests only and must never reach
     the solvers. One more piece of the same trap, guarded there by comment:
     SystemGrob.AddColumn alone does NOT put a column in the system's element
     list, and PreProcessing walks the element list — a fixture must call
     TypesetGrob as well, or PreProcessing silently prebreaks nothing.

TWO CORRECTIONS TO THE O7 DECISION RECORD, both now measured and test-pinned:

  * "~187 rules" is the count of NONTERMINALS WITH RULES, not of productions.
    parser.yy has 633 productions once each | alternative is counted separately
    and Bison's mid-rule rewrite is included. 633 is what the generator works
    over; 479 of them carry an action body to hand-port.

  * "the 36 precedence declarations" matches neither figure in the file.
    parser.yy has TEN %left/%right/%nonassoc declarations -- Bison assigns one
    precedence LEVEL per declaration, and conflict resolution compares levels,
    so ten is the number that decides shift/reduce outcomes. 24 symbols carry
    precedence.

  Both are asserted in GrammarShapeTests/GrammarInventory with the correction
  written next to them, so they cannot drift back.

DELIBERATE CHOICES IN THE READER

  * Unknown Bison declarations are a HARD ERROR
    (UnsupportedBisonFeatureException), never a skip. Generating the tables
    in-repo only buys anything if a re-sync onto a grammar using a new feature
    stops at sync time; a silently skipped declaration changes the language the
    parser accepts with nothing to say so.

  * Action bodies are extracted as OPAQUE TEXT and never parsed. They are C++
    and they are hand-ported; the reader's job is to know a rule HAS one and to
    key it, not to understand it. The brace matching does have to respect C++
    strings, character literals and comments -- an action containing '{' is not
    hypothetical in this grammar.

  * Mid-rule actions are REPRODUCED as Bison rewrites them: `a: B { x } C`
    becomes `a: B $@1 C` plus `$@1: /*empty*/ { x }`. The rewrite changes the
    grammar -- the synthesized empty rule is a real reduction point and can
    create conflicts -- so hiding it would make the generated tables differ from
    Bison's for reasons that never showed up anywhere.

  * `error` is declared as a built-in terminal. Nothing in parser.yy declares
    it, and left undeclared it reads as a nonterminal with no rules, which makes
    every error-recovery rule unreachable.

  * Rules are keyed by IDENTITY (the production written out, plus an ordinal for
    genuine duplicates), not by index. An index shifts the moment anything is
    inserted above it, so a re-sync adding one rule near the top would appear to
    change every action below it.

NOT YET DONE IN TRACK P

  The LALR(1) table construction, the driver, the modal lexer and the 479 rule
  actions. Also the ONE-TIME fidelity anchor: real Bison has NOT been run at
  this pin, so tools/parser-baseline/ does not exist yet. Bison is not installed
  on this machine and installing it needs Jeremy's approval; it is a one-time
  need, and neither a downstream build nor an upstream re-sync ever wants it.

ADDED 2026-08-03 (eighth pass) -- THE FIRST ORACLE COMPARISON, AND WHAT IT SAID
-------------------------------------------------------------------------------

The Milestone 5 comparator has now been run against the port for the first time,
on `{ c'4 }`. Verdict: GLYPHS-DIFFER -- up the ladder from MISSING, which is
exactly the position first light was expected to reach. Two findings came out of
it, and the second one changes a priority.

1. THE PORT'S SVG WAS NOT WELL-FORMED XML. Every glyph reference is an
   xlink:href, and SvgBackend never bound the xlink namespace. A browser renders
   it happily; an XML parser refuses it. The comparator's FIRST verdict was
   UNPARSEABLE, and nothing in the port's own 21 backend tests had noticed,
   because none of them parsed the output as XML. Fixed, and pinned by a test
   that parses a rendered document rather than string-matching it.

2. THE COMPARATOR CANNOT COMPARE MUSIC GLYPHS BETWEEN THE PORT AND LILYPOND,
   and the reason is structural rather than a defect on either side.

   LilyPond 2.27.2's SVG backend embeds each glyph's OUTLINE as a <path> with a
   scaled transform. It does this unconditionally -- -dsvg-woff does not change
   it, checked. The port's SvgBackend emits <use xlink:href="#noteheads.s2"/>,
   which keeps the glyph NAME visible and leaves outlines to the font layer.

   So the comparator sees, for the same music:

       reference   <path:1> x2, <path:5> x1, <text> x1
       candidate   noteheads.s2 x1, clefs.G x1, clefs.G_change x1

   Its <use> branch -- written in Milestone 5 -- is DEAD against real LilyPond
   output. Its <path:N> branch is a deliberately coarse signature (the README
   says so: "the exact control points are the last thing a port gets right").
   Milestone 5's two-directional validation did not expose this because BOTH
   sides of it were LilyPond output, and the coarse path signature does vary
   with staff size, so the check still discriminated.

   CONSEQUENCE, AND IT IS A PRIORITY CHANGE: reaching glyph-level comparison
   needs the port to emit outlines, which needs a CFF CHARSTRING INTERPRETER.
   That piece is recorded above as deferred, on the grounds that it is "only
   wanted for skyline tracing" (stencil-integral.cc). That is no longer true --
   it is also what stands between the port and its only correctness oracle.

   The alternative, teaching the comparator to resolve <use> names against the
   font, was considered and is worse: it would compare the port against its own
   idea of the glyph inventory rather than against LilyPond's rendered output,
   which is the one thing the oracle exists to avoid.

WHAT THE REMAINING DIFFERENCES ARE, ALL ALREADY KNOWN

   * The reference carries a <text> tagline and a bar line; the port has neither
     (no page layout, no Bar_engraver -- see EngraveResult.MissingTranslators).
   * The port emits TWO clefs, clefs.G and clefs.G_change. Not a defect: with no
     Bar_engraver nothing sets forbidBreak, so break_allowed is true at every
     timestep and Clef_engraver makes a clef at each. Upstream does the same
     under the same conditions.
   * No placement comparison happened at all, because the inventories differ
     first. Spacing is unported, so every column is still at x = 0.

ADDED 2026-08-03 (ninth pass) -- TRACK P: the generator, the driver, the fences
-------------------------------------------------------------------------------

The machinery of decision O7 is BUILT AND VERIFIED. The bulk translation work --
the lexer's nine remaining modes and 476 of the 479 rule actions -- is not.

WHAT REAL BISON SAID, TWICE
...........................

The one-time baseline (tools/parser-baseline/, GNU Bison 3.8.2, 913 states, zero
conflicts) corrected the port TWICE, and neither error was findable any other
way.

  1. THE GRAMMAR READER WAS WRONG BY 17 ON THREE COUNTS. It reported 633
     productions, 32 mid-rule actions and 221 nonterminals; Bison has 616, 15
     and 204. Seventeen rules are written `... { action } %prec X`, and the
     reader treated the action as a MID-RULE action because something followed
     it. %prec is an ANNOTATION on the enclosing rule, not a symbol. Reading it
     the other way invents seventeen productions and seventeen nonterminals,
     each a reduction point the real parser lacks.

     The reader's own tests were green, the grammar was structurally consistent,
     and every invented rule was individually plausible. Only the automaton knew.

  2. THE GENERATOR BUILT TWO STATES BISON DOES NOT HAVE. Precedence resolution
     DELETES shift actions -- when `%left '-'` makes `script_dir: '-' •` reduce
     rather than shift, the '-' transition goes with it -- and Bison then removes
     whatever became unreachable. A generator that resolves conflicts but keeps
     the states produces the SAME PARSER with a different state count, after
     which nothing it says about itself can be checked. LalrGenerator now prunes,
     which is worth exactly the two states plus the two they alone led to.

A THIRD THING THE DRIVER FOUND, WHICH IS BEHAVIOUR RATHER THAN COUNTING
.......................................................................

  Bison's $default is not a table compression. A state with a default reduction
  NEVER reports an error: it reduces, and the error surfaces later, in whatever
  state the reduce lands in. That decides which `error` rule can recover.

  Without it, `lilypond: lilypond error` -- the production that lets LilyPond
  report every error in a file rather than stopping at the first -- could never
  fire, because the error was detected in state 0 before `lilypond` had been
  reduced at all.

  And Bison SUPPRESSES the default in exactly the states that can shift `error`:
  of its 913 states, 703 carry a $default and the 13 that shift `error` carry
  none. If they did, recovery could never fire in them. Measured from the
  baseline and asserted.

DELIBERATE CHOICES
..................

  * The item-set comparison against the baseline ignores STATE NUMBERING. Bison's
    numbers come from its own exploration order, which is an artifact; what is
    compared is the SET of item sets, which is numbering-independent and is what
    decides how the parser behaves.

  * %nonassoc plants an EXPLICIT error action rather than removing the entry, so
    that the state's default reduction cannot quietly take it over. `a < b < c`
    has to be rejected -- that is the only reason %nonassoc was written.

  * The baseline reader is QUOTE-AWARE throughout. The obvious implementation
    finds the lookahead list with IndexOf('['), and this grammar has
    `br_bass_figure: '[' bass_figure` -- so that bracket is inside a character
    literal, and truncating there silently mis-reads every state containing the
    rule. It cost a real debugging session, chasing a difference that was in the
    checker rather than in the thing being checked.

  * Rule actions are keyed by IDENTITY, never by rule number. A number shifts the
    moment anything is inserted above it, so a re-sync adding one rule near the
    top would silently re-point every action below it. RuleActionTable.Bind
    REFUSES an identity the grammar no longer has rather than dropping it.

  * The lexer is a hand-ported modal scanner over .NET regular expressions
    anchored with \G, reproducing flex's longest-match-then-earliest-rule and its
    start-condition STACK (%option stack -- modes nest, so a \markup inside
    \lyricmode returns to lyrics). %option nodefault is reproduced too: an
    unmatched character is reported, not echoed.

WHAT IS NOT DONE IN TRACK P
...........................

  * ~~The LEXER's token-producing rules~~ DONE 2026-08-03: ALL FOURTEEN start
    conditions are ported and tested -- notes, chords, figures, lyrics, markup,
    quote, commandquote, incl, maininput and the rest. What the scanner still
    DELEGATES is the DATA those rules consult (note-name and keyword tables,
    markup signatures, a Scheme reader), through Lexing/ILexerHost.cs -- the same
    seam upstream reaches through Lily_parser and Guile.
    LexerCoverage.DelegatedToHost names all five.

    One deliberate divergence: upstream's "pseudo backup rules" -- the
    {SYMBOL}/[-_] trailing-context patterns -- are NOT reproduced. They exist to
    shape flex's generated tables (avoiding backup states) and have no effect on
    which token comes out; the port's scanner does not generate tables, so they
    would be noise.

  * 476 of the 479 RULE ACTIONS. The worklist is computed from the committed
    manifest (Actions/rule-manifest.tsv) rather than maintained by hand, so
    porting one removes it by construction and a rule that stops existing cannot
    linger on it.

  Neither is a design question -- the seams are built and verified. Both are
  translation.

  EntryPointClosure (PortLedger.cs)

    Gate G3, measured rather than listed. Everything in entry-points.tsv is
    installed as a stub first and the ported primitives overwrite the bindings
    afterwards, so "is this name still bound to the object we installed" is the
    only honest test of whether it is implemented. EntryPoint.Stub exists to
    make that reference comparison possible. A name-list would drift; this
    cannot.

    An entry point whose binding VANISHED counts as stubbed, not implemented:
    the Scheme cannot call it either way, and the other answer flatters G3.

    MEASURED BASELINE, 2026-08-04: 234 of 737 implemented, 503 still stubs.
    EntryPointClosureTests asserts it as a FLOOR, so a session that raises the
    number need not come back and edit it, but a session that breaks a
    registration fails.

  tools/regression-harness/ratchet.py + pass-manifest.tsv

    The per-file floor. The manifest records the BEST VERDICT EVER ACHIEVED per
    reference page, and a run must meet or beat every row. A pass COUNT would
    hide a swap -- one file gaining MATCH while another loses it -- so the gate
    is per-file and asymmetric by design. `ratchet.py self-test` proves the
    logic, including that a net-positive swap still fails.

    compare-output.py grew a `--tsv PATH` option to emit machine-readable
    per-file verdicts; its human report is not parseable and never was.

    pass-manifest.tsv is COMMITTED EMPTY. The port cannot engrave a regression
    file end to end until EPG3, and the verdicts only become meaningful at EPG4.
    The machinery lands first on purpose: a ratchet retrofitted afterwards
    records whatever the port happened to be doing that day, which is how a
    suite ends up enshrining its own bugs.

  Suite mode (EnginePrimitives.SuiteModeRequested / ThrowingScope)

    LILYPORT_THROW_ON_UNPORTED=1 turns every placeholder into a failure.

    It arms at the END of LoadViaLilyScm and not a line earlier. Loading is the
    one phase that legitimately calls unported primitives -- LilyPond's Scheme
    builds its tables by calling into C++ -- and a throwing stub there aborts
    the file and hides every later call in it. After the layer is loaded, a

POSITIONS ARE CHARACTER OFFSETS, NOT BYTE POINTERS

  Upstream's Input holds two `char const *` into a UTF-8 buffer and Source_file
  works in the same currency; get_counts explicitly skips UTF-8 continuation
  bytes so that its column count comes out in CHARACTERS.

  The port holds a SourceFile plus two character offsets. Line and column come
  out identical by construction -- counting .NET chars, with a surrogate pair
  counted once, is the same measurement upstream's continuation-byte skip
  performs. The one figure that differs is the WITHIN-LINE offset, a character
  offset here and a byte offset upstream; it is used only to split a line for
  the error caret, and both split at the same place.

  SourceFile.OffsetOfLineColumn is NEW, with no upstream counterpart: upstream's
  parser carries pointers, so it never needs to go the other way. This port's
  lexer reports line and column, and that method is the bridge back.

Input IS A CLASS, NOT A VALUE TYPE

  Upstream copies Input by value everywhere. Here it is a reference type so an
  origin can be stored in a Scheme property as one object, which is what
  MusicObject.SetSpot has always wanted. Spot() therefore copies EXPLICITLY
  where upstream's copy is implicit in return-by-value; SetSpot copies fields
  rather than rebinding, so an origin already handed out does not change under
  its holder.

Diagnostics IS AN INTERFACE

  Upstream reaches it by multiple inheritance (class Music : public
  Smob<Music>, public Diagnostics). C# has none, so IDiagnostics is an interface
  with default implementations -- same routing, same fallbacks, no base-class
  slot spent. Nothing implements it yet; Grob, MusicObject and MusicIterator
  adopt it when their groups touch them.

THE MUSIC-FUNCTION CALL PROTOCOL IS NOT SCHEME'S, AND IS TRANSLATED LITERALLY

  When an optional argument's predicate REJECTS the next actual argument, that
  argument is NOT consumed: the default is substituted, and every FOLLOWING
  optional is unconditionally defaulted too. \default triggers the same skip
  explicitly, and *unspecified* is its Scheme spelling -- which IS consumed.

  Trailing optionals need no *unspecified* stand-in, because the end of the
  argument list is recognisable on its own. That is what makes (key) in Scheme
  mean what \key \default means in LilyPond.

  The loop shape, the do/while over consecutive optionals and the two separate
  trailing passes are load bearing. MusicFunctionTests pins each case; a tidier
  rewrite rebinds arguments silently rather than failing.

  Signature values are CLONED on the way in (a default is shared by every call
  that uses it, and music is mutable), and the RESULT is not (it is freshly
  made and has no other owner). That asymmetry is upstream's.

MusicFunctionSupport IS NEW-IN-FAMILY

  Upstream reaches %location, argument-error and music-function-call-error
  through lily/lily-imports.cc's Scm_module/Variable pairs -- Guile module
  handles this port does not have (lily-imports.cc is a no-port ledger row).
  The replacements look their targets up BY NAME at the moment of use, because
  ly-syntax-constructors.scm is an on-demand module: caching a variable at
  install time captures whatever was bound before it loaded, which is nothing,
  and the failure looks like a music function that silently reports no errors.

FLOWER GAINED Warn.DeprecationWarning

  flower/warn.cc's deprecation_warning was never ported, and it DE-DUPLICATES:
  each distinct message is reported once. ly:deprecation-warning was bound to
  the generic sink, so the port repeated a warning that upstream prints once.

  clears it (a run is one document), but a test run is many documents in one

OUTPUT DEFINITIONS HOLD A REAL MODULE (corrected 2026-08-04, EPG1)
-------------------------------------------------------------------------------

  Output_def::scope_ is a Guile module upstream, and this file used to record
  the port's dictionary as an invisible difference: "nothing in the engine
  treats an output definition's scope as a module -- it is only ever read and

THE DEFECT THE STAND-IN WAS HIDING: TRANSLATOR LISTENERS WERE ON THE WRONG
DISPATCHER
-------------------------------------------------------------------------------

  Translator::ListenTo registered on Context.EventSource. Upstream's
  Translator_group::connect_to_context takes c->events_below () and registers
  every translator's listeners THERE. The difference is invisible while every
  engraver lives in the context its events are addressed at -- which is exactly
  what the hand-built stand-in tree produced -- and it silently deafens every
  ancestor-context engraver the moment a real Staff sits above a real Voice.

  Fixing it alone was not enough, and the second half is the more interesting
  one. The port had never done upstream's

      events_below ()->register_as_listener (event_source_)

  and had instead compensated by making Context::SendStreamEvent broadcast on
  BOTH dispatchers. That compensation cannot work, because the iterators do not
  go through SendStreamEvent: Music_iterator::report_event broadcasts on the
  event source directly, upstream and here alike. So with listeners moved to
  EventsBelow, note events stopped being heard at all -- the note head vanished
  while the clef and the staff symbol stayed, because those two engravers do
  their work without listening.

  Both halves are now upstream's: the chain is registered in the Context
  constructor, and SendStreamEvent broadcasts once, on the event source.

DELIBERATE DIVERGENCES (EPG2)
-------------------------------------------------------------------------------

  Context (Symbol, string) -- a name-only constructor building a SYNTHETIC
  Context_def carrying nothing but the name. Upstream has no such constructor
  because upstream always has an output definition to read a real one out of.
  It exists for fixtures that exercise the dispatcher, the property lookup or
  one engraver without standing up the whole init layer, and such a context has
  an empty acceptance set -- so it is a bottom context until the fixture says
  otherwise through Context.Acceptance.

  translator-dispatch-list.cc -- the interface-keyed acknowledger lookup lives
  in SchemeEngraver.Acknowledge rather than in a per-group memoised
  Engraver_dispatch_list. Upstream's list is a CACHE keyed on the grob's name,
  and the port has nothing to key it on: the C# engravers filter inside their
  own AcknowledgeGrob overrides rather than registering per-interface
  acknowledgers. The set of procedures that run, and the order they run in, is
  the same.

  PerformerGroupPlaceholder stands in for Performer_group and Score_performer
  until EPG19. It is a real, empty Translator_group rather than a null return,
  and the difference matters: a null group makes \midi fail at context creation
  with a programming error, whereas an empty one builds the same context tree
  and simply produces no performance. That keeps ly/performer-init.ly loadable.

  Context_handle carries no destructor assertion. Upstream asserts the handle
  was cleared, because garbage collection makes RAII unreliable and it wants a
  leak detected early; C# has no deterministic destructor to assert in and a
  finalizer would fire on the collector's thread. The owner's obligation is
  unchanged.

  GlobalContext registers all five of Context's listeners (CreateContext,
  RemoveContext, ChangeParent, SetProperty, UnsetProperty). Upstream's
  Global_context registers only CreateContext and Prepare, "the most basic
  stuff to bootstrap the context tree". The port's set is a superset, so a \set
  addressed at Global takes effect here and is ignored upstream.

G4's MEASUREMENT IS COMPUTED (EPG2)

THE DEFECT THIS FOUND, AND IT IS THE ONE TO REMEMBER: A SKYLINE PAIR IS A CONS
-------------------------------------------------------------------------------

  The port had a SkylinePair class and stored it directly as the value of the
  horizontal-skylines grob property. There is no skyline-pair object in Scheme.
  scm/c++.scm defines

      (define-public (ly:skyline-pair? x)
        (and (pair? x) (ly:skyline? (car x)) (ly:skyline? (cdr x))))

  and lily-guile.cc's scm_conversions<Skyline_pair> is scm_cons of the two
  smobbed skylines. So the property is a CONS, and a CLR object in that slot
  fails ly:skyline-pair? -- which is the property's own type predicate --
  and breaks every Scheme reader that expects to car it (skyline.scm,
  paper-system.scm).

  This was invisible until EPG4, because nothing had ever WRITTEN
  horizontal-skylines: the property was only ever read, and reading an unset
  property answers '() rather than a wrong type. The first write is what
  surfaced it. SkylinePair now carries ToScheme/FromScheme -- including
  upstream's guard that the first skyline must face DOWN/LEFT and the second
  UP/RIGHT, which upstream raises on rather than silently swapping -- and
  every reader goes through them.

  The same class of defect, one layer along: the spacing engraver writes
  shortest-playing-duration and shortest-starter-duration, whose type
  predicate is positive-musical-length-as-number?. A flower Rational is not a
  Scheme number, so those writes were rejected too. They go through
  SchemeConvert.FromRational now. The INEXACT case is the one that bites:
  Rational::infinity reaches Scheme as +inf.0, a real, and
  Paper_column::is_musical reads it back -- so PaperColumn's rational reader
  had to learn doubles, or a column where no note starts would have been
  silently reclassified as non-musical.

-------------------------------------------------------------------------------
THE OTHER DEFECT: A LISTENER REGISTERED IN A CONSTRUCTOR TAKES THE TREE DOWN
-------------------------------------------------------------------------------

  Spacing_engraver has ADD_LISTENER (spacing_section). The port's first cut
  called ListenTo from the engraver's constructor. A context's below-dispatcher
  is wired up AFTER its translators are allocated, so that call failed -- and
  because it failed while the Score context was being built, there was no Score
  engraver left to report anything. The symptom was an empty drawing with no
  diagnostic at all.

  Every port engraver with listeners registers them in ConnectToContext and

WHERE line-width COMES FROM, AND THE TWO REASONS IT WAS NOWHERE (EPG4)
-------------------------------------------------------------------------------

  The spacing solver takes a line width. The port had none, and fell back to a
  guess; both halves of the reason are worth recording, because neither was
  visible until something asked for the number.

  FIRST: Output_def::normalize was never ported. output-def.cc's ledger row said
  "ported", which is true of the TYPE -- but normalize is the ONLY thing that
  ever computes line-width. scm/paper.scm's set-paper-dimensions deliberately
  REMOVES line-width from the paper module (a stale one from lilypond-book is
  worse than none), so between paper setup and normalize there is genuinely no
  line width anywhere in the system. It is ported now, asymmetric
  unstated-margin cases and consistency checks included.

  SECOND: the score's layout was parented onto the book's paper only when it
  had no parent at all. Score::book_rendering does it UNCONDITIONALLY --
  scale_output_def, then def->parent_ = layoutbook. The port's $defaultlayout
  arrives already parented to the ORIGINAL $defaultpaper, while ly:make-book
  hands the book a CLONE; so every variable the book's paper computed resolved
  to nothing from the score's side, and normalize could not have helped even
  once it existed. Both are fixed; the scaling half of scale_output_def stays
  at 1 with the rest of the D20 divergence.

  Upstream calls normalize from Book::process. The port calls it from
  BatchRunner.ScoreLayout -- same object, same point in the sequence -- until
  EPG16 lands the real book path and it can move to where it belongs.

  Measured effect on the 2,146-file sweep: 121 of the 915 files that produce
  SVG went from a zero-width page to a real one, and 108 from every grob at
  x = 0 to real horizontal positions. The comparator's verdict does not move
  yet (897 pages stay at the GLYPHS-DIFFER floor) because it cannot grade
  positions while the glyph inventories differ -- that is EPG13's upgrade, and
  it is why the plan slots EPG13 immediately after EPG4.

EPG13 -- TEXT INTERFACE, GLYPH OUTLINES AND FONT ASSETS (2026-08-05)
-------------------------------------------------------------------------------

  WHERE THE FONTS LIVE

  lily/all-font-metrics.cc  ->  Fonts/AllFontMetrics.cs, Fonts/FontAssets.cs

  Upstream finds font files through FontConfig, seeded with LilyPond's
  installed data directory. The port has no FontConfig dependency and now
  carries every font INSIDE the assembly as an embedded resource, exactly as it
  already carried the ly/ and scm/ layers. A consuming application may put a
  directory in front of the embedded copies (FontAssets.SearchPaths); nothing
  can make the lookup fail.

  This replaced a directory probe that walked up six levels from the running
  assembly looking for assets/fonts/otf. Six levels reaches the repository root
  from a project under src/, and falls exactly ONE level short from
  tools/regression-harness/BatchDriver. The consequence was not subtle in
  effect and completely silent in appearance: the entire regression sweep ran
  with NO music font at all. 354 files died on ly:font-get-glyph against a null
  font, and the 915 that did produce SVG produced staff lines and stems with
  not one note head among them -- while the only diagnostic was one
  "cannot find font: `emmentaler-20'" warning per file. Embedding removes the
  failure mode rather than lengthening the probe.

  WHERE GLYPH OUTLINES COME FROM

  Fonts/SvgFontOutlines.cs (new-in-family), from scm/output-svg.scm

  Music glyph outlines are lifted VERBATIM out of the shipped .svg font, which
  is what upstream's own SVG backend does (music-string-to-path ->
  cache-font -> extract-glyph). They are NOT rasterised from the OTF's CFF
  charstrings, even though the port can now do that: an independently produced
  outline would be the same SHAPE and a different STRING, and the parity
  yardstick compares strings.

  The units-per-em divisor is hardcoded at 1000, carrying upstream's own
  "TODO: not urgent, but do not hard-code this value" comment. Every shipped
  music font is drawn on a 1000-unit em, so the two agree.

  THE CFF CHARSTRING INTERPRETER

  Fonts/CffFont.cs, Fonts/CharstringRun.cs (new-in-family)

  Written from the Type 2 Charstring Format specification, because a glyph's
  INK extent is recorded nowhere in an OpenType font -- it is a property of the
  outline, so the only way to learn it is to run the program. Text layout needs
  it: how tall a line of text is decides what the engraver puts above and below
  it.

  Validated against an oracle that ships in this repository. Every music font
  is vendored twice, once as an OTF holding glyph PROGRAMS and once as an SVG
  font holding the same glyphs as finished OUTLINES, both produced from one
  source by the font build. CffOutlineTests runs all 600-odd charstrings and
  compares the control hull to the SVG outline's, to within 1.5 units of a
  1000-unit em.

  DIVERGENCE: the bounding box is the CONTROL HULL, not the true ink extremum
  -- a cubic's control points are included rather than the curve's own maxima.
  The hull always CONTAINS the curve, so a text line is never reported shorter
  than it draws, which is the direction that matters when an engraver reserves
  room from it.

  TEXT FONTS

  lily/pango-font.cc  ->  Fonts/TextFontMetric.cs  (ledger: no-port, replaced)
  lily/pango-select.cc ->  Fonts/FontInterface.cs   (ledger: no-port, replaced)

  There is no Pango, no FontConfig and no FreeType. What survives verbatim is
  the CONTRACT, in two places that the rest of the system depends on exactly:

    1. The stencil expression is (utf-8-string DESCRIPTION TEXT INNER), and the
       DESCRIPTION is a Pango-style string -- "serif Bold Italic 8.25". The SVG
       backend recovers the family, weight, slant and size from it by pattern
       matching, using upstream's own regular expression. The style words and
       their order are therefore not free: a different order does not fail, it
       silently lands inside the font family name.

    2. Horizontal extent is the advance sum, from hmtx. VERTICAL extent is the
       INK extent, from the charstrings. Upstream takes exactly this split --
       logical rectangle for X, ink rectangle for Y -- in
       pango_item_string_stencil, and reading Y off the logical rectangle
       instead would make every line of text the same height.

  The INNER expression is left empty. It is the glyph-by-glyph drawing that the
  utf-8-string encapsulation replaces, and it is consumed only by backends that
  do not handle utf-8-string themselves. The port's SVG backend does handle it,
  and SVG is the parity yardstick (D15), so filling it in would be an
  unverifiable guess rather than a fidelity gain.

  Pango's scale_ member is not reproduced. Its constants cancel: an advance
  measured at PANGO_RESOLUTION dots per inch, multiplied by
  INCH_TO_BP / (PANGO_SCALE * PANGO_RESOLUTION * output_scale), leaves
  size / output_scale, and that is what TextFontMetric.Scale computes.

  D23 FALLBACK CHAIN

  Fonts/TextFace.cs

  serif      -> C059-*          -> texgyreschola-*
  sans       -> NimbusSans-*    -> texgyreheros-*
  typewriter -> NimbusMonoPS-*  -> texgyrecursor-*

  and STOPS. Upstream's 00-lilypond-fonts.conf continues into DejaVu and Noto
  CJK, which it does not ship. There is NO system-font fallback: a code point
  no face covers draws missing-glyph tofu by design, and the .notdef glyph
  keeps its own advance so the tofu takes up room instead of collapsing the
  line.

  The face file names are spelled out rather than generated from a template,
  because the three collections do not agree on how to name a face: URW writes
  "Regular" and "BoldItalic", C059 writes "Roman" and "BdIta", and TeX Gyre
  writes everything in lower case. A template silently produces a name that
  does not exist, and a missing face does not fail -- it drops out of the chain
  and leaves text measured by the FALLBACK font.

  THE BACKEND OPTION

  Bootstrap/LilyPondScheme.cs

  `backend` is set to 'svg and `music-strings-to-paths` to #t once the scm/
  layer has loaded. Upstream's option defaults to 'ps because upstream ships
  all three backends; the port has exactly one (D15). This is not cosmetic:
  ly/paper-defaults-init.ly branches on the same option to choose text font
  family names, and under 'ps it picks the FontConfig aliases "LilyPond Serif",
  "LilyPond Sans Serif" and "LilyPond Monospace" where the SVG backend wants
  the generic CSS families "serif", "sans" and "monospace". Those names are
  written verbatim into every text element.

  ENGRAVING IN OUTPUT UNITS  (pulled forward; upstream lily/paper-def.cc)

  Layout/OutputDef.cs (ScaledClone), CodeBrix.LilyPort/BatchRunner.cs

  Upstream scales BOTH the book's paper (Paper_book's constructor) and each
  score's layout (Score::book_rendering) by the paper's output-scale before a
  single grob is made, so engraving happens in output units -- one unit is one
  staff space -- and a coordinate reaching a stencil needs no further
  conversion. The port did neither, and the D20 note recorded the scale as
  staying at 1.

  Skipping it does not fail. Everything is laid out in millimetres instead and
  the whole page comes out scaled by about 1.757 with no diagnostic anywhere,
  which is why it survived EPG3 and EPG4. It is fixed here because EPG13's
  purpose is to make the comparator able to grade POSITIONS, and no position
  could ever have matched.

  output-scale and staff-height are deliberately NOT in the paper's
  dimension-variables list: the first has to survive scaling so the framework
  can convert back to millimetres for the page, and the second is read in
  POINTS to size fonts.

  ONE PROCESS PER INPUT FILE  (harness; no upstream analogue)

  CodeBrix.LilyPort/LilyPondInit.cs (RestoreDefaults)

  Upstream engraves one input file per process, so the defaults a file mutates
  die with it. The batch runner shares one session across 2,146 files, and the
  mutations are not hypothetical: a toplevel \paper block rewrites the shared
  definition IN PLACE, and #(set-global-staff-size 30) does something else
  again -- it CLONES the paper, scales the clone, and rebinds the toplevel
  $defaultpaper identifier to it, deliberately leaving the original object
  untouched ("maybe someone still refers to the old one").

  Both halves have to be undone, and the second is the one that bites:
  restoring only the object's variables fixes nothing, because the next book
  still picks up the clone by name. Measured: before this, the two
  absolute-dimensions-* files at the head of the suite rescaled every file
  swept after them -- staff line thickness read 0.0781 where the oracle says
  0.1000 -- and it looked like a port-wide unit error rather than leakage.

  LIMIT: this restores the value of every variable the definitions had after
  initialisation, which covers the numeric leaks. A variable a file INVENTS is
  left in place, because the scope has no unbind.

  SKYLINES FROM STENCILS

  lily/stencil-integral.cc  ->  Layout/StencilIntegral.cs

  All ten callbacks land. Eight are exact: the four from-extents ones use the
  grob's own bounding box, and the four from-element-stencils ones merge the
  children's skylines (Shift along the horizon axis, Raise along the other --
  upstream's comment records that getting those two the wrong way round cost
  six months).

  DIVERGENCE, and the largest one in this pass: the two from-stencil callbacks
  take the stencil's EXTENT BOX rather than walking the stencil expression.
  Upstream turns each drawing command into segments and flattens every Bezier,
  so a slur's skyline follows the curve; this port produces its rectangular
  hull. That is upstream's OWN fallback -- the branch it takes for expressions
  it cannot decompose, such as embedded PostScript.

  The consequence is bounded and one-directional: a box always CONTAINS the
  outline, so nothing is ever placed too close, and the cost is extra space
  around non-rectangular grobs rather than a collision. The expression walk
  plus Lazy_skyline_pair is the one EPG13 work item left owed, and it wants to
  land with or before EPG10-EPG12 (beams, ties, slurs), whose whole point is
  outlines that are not boxes.

  CLOSED 2026-08-05 (later the same day) -- the walk landed. See THE STENCIL
  EXPRESSION WALK at the end of this file; the only case that still takes the
  box is a stencil containing TEXT, and that one is recorded there.

  PURE VARIANTS

  The pure-* skyline callbacks answer the ordinary extents. The port has no
  pure-property machinery yet -- that is unpure-pure-container.cc, EPG15 -- and
  answering the ordinary extent is what a grob declaring no pure callback would
  give anyway.

ADDED 2026-08-05 (EPG13 carry-forward) -- THE STENCIL EXPRESSION WALK
-------------------------------------------------------------------------------

  lily/include/lazy-skyline-pair.hh  ->  Layout/LazySkylinePair.cs
  lily/stencil-integral.cc           ->  Layout/StencilIntegral.cs  (the walk)
  lily/freetype.cc Path_interpreter  ->  Fonts/CffFont.cs  (OutlineWalker)

  The item EPG13 left owed. The two from-stencil callbacks now WALK the stencil
  expression instead of taking its bounding box: every draw-line, dashed-line,
  circle, ellipse, partial-ellipse, round-filled-box, polygon, path and
  named-glyph is turned into segments, curves are flattened at one segment per
  0.2 output units, and the structural heads (combine, translate, scale, rotate,
  grob-cause, color, output-attributes, with-outline) carry the transform down.

  WHAT IS FAITHFUL, DELIBERATELY, EVEN WHERE IT LOOKS WRONG

  * A curve's LAST piece is added as a plain segment, not as a contour segment,
    so it lands in both skylines while its earlier pieces land in one. That
    asymmetry is upstream's, in Path_interpreter::curve3to. Kept: the
    faithfulness rule says a plausible tidy-up is a parity bug.
  * dashed-line is measured as one solid run from the origin to (dx, dy). The
    gaps are ignored, which over-reserves; upstream does the same.
  * An unknown head contributes nothing and raises NO warning. Upstream's
    reason is in a comment: stencil-expression.cc's registry is what validates
    heads, and a complaint here would be a second, worse copy of that check.
  * A malformed path warns and keeps the commands it had already grouped,
    rather than throwing.

  DIVERGENCE 1 -- the glyph outline comes from the charstrings, not FreeType

  Upstream traces a named glyph with FT_Outline_Decompose and recovers the
  design-units-to-output-units factor by DIVIDING two boxes: FreeType's glyph
  metrics and FreeType's outline bounding box, which round differently. The
  port has one source for both -- the Type 2 charstring interpreter, which
  EPG13 built and validated against the shipped SVG fonts -- so that ratio is
  the scale factor itself: the font's drawing size over its units per em. It is
  the same number SvgBackend scales the same outline by, and the traced result
  agrees with the LILC-declared extents of noteheads.s2 to within 0.002 staff
  space (StencilIntegralTests).

  A charstring leaves the contour-closing segment implicit where FreeType's
  decomposer emits it, so OutlineWalker emits it itself when a contour ends.

  Contours are traced COUNTER-CLOCKWISE, the PostScript/CFF convention. A
  TrueType face would need the other one; getting it backwards produces a
  plausible skyline that is inside out, with no error.

  DIVERGENCE 2 -- TEXT STENCILS still take the extent box

  Upstream's utf-8-string expression carries, as its fourth element, the
  glyph-string stencil Pango shaped -- and the walk recurses into it. The port
  has no Pango: TextFontMetric.TextStencil measures the run through the D23
  font chain and leaves that fourth element EMPTY, so there is nothing to
  recurse into.

  Walking such a stencil anyway would be the dangerous answer. A stencil that
  COMBINES text with drawing would yield a skyline covering the drawing alone,
  silently omitting the text -- and a skyline that omits ink is the one error
  direction that causes collisions. So SkylinesFromStencil checks for a text
  node anywhere in the expression and falls back to the whole stencil's extent
  box when it finds one. That is exactly the pre-walk behaviour, preserved for
  this one case: conservative, never a collision.

  glyph-string itself is NOT handled, because the port never emits it.

  WHEN TO CLOSE IT: text does not reach a swept page yet -- in-score text needs
  Text_engraver (EPG14) and the tagline needs page layout (EPG16). EPG14 is the
  session where per-glyph text outlines become measurable and worth writing;
  the machinery to do it is already here (TextFontChain plus CffFont's
  AddOutlineToSkyline, which is face-agnostic).

  PURE VARIANTS are unchanged: they still answer the ordinary extents, pending
  unpure-pure-container.cc in EPG15.

DELIBERATE DIVERGENCES (EPG5)

    rest-collision multiplies by a Direction that can take this path.

THE PREMATURE ALIGNMENT TRIGGER, AND THE PURE STAND-IN THAT ABSORBS IT (EPG7)
-------------------------------------------------------------------------------

  The EPG4 note on Spacing_interface::skylines -- "it does compute and cache a
  Y offset earlier than upstream would, which is a thing to re-check when
  EPG7's vertical alignment starts moving staves" -- came due, and it was the
  single hardest thing in this pass.

  Upstream never reads a staff's unpure Y position before line breaking: the
  early readers go through the pure machinery, and a BARE unpure procedure
  answers #f in a pure context (call_pure_function), so an early pure read of
  a parent-positioned grob yields 0 WITHOUT running the alignment and WITHOUT
  consuming the one-shot offset. The port's spacing reads the REAL coordinate
  (the recorded EPG4 stand-in), which triggers ly:grob::y-parent-positioning
  -> positioning-done -> the alignment, DURING System::pre_processing -- when
  the alignment has no system yet and the columns have no X positions.

  Two consequences had to be dealt with, and both cost a debugging round:

  1. Upstream's align_elements_to_ideal_distances REFUSES without a system.
     Refusing here burns every staff's one-shot offset at zero for good (a
     grob offset is computed exactly once and the property deleted), so every
     multi-staff score would keep stacking staves -- the exact defect class
     this group exists to remove.

  2. Letting the early call run the UNPURE minimum-distance stacking instead
     poisons the render: the skylines read stencils, and a STAFF SYMBOL's
     stencil depends on column X positions that are still all zero, so the
     staff lines cache at zero length and the final drawing collapses. This
     was measured, not theorized: clef-force.ly's staff lines went from
     x2=102.38 to x2=-0.05 before the fix.

  THE STAND-IN: when align_elements_to_ideal_distances finds no system, it
  takes upstream's own currency for before-line-breaking questions -- the
  PURE stacking over the full score range (start 0, end INT_MAX). Its
  skylines are flat boxes over the groups' Y extents (upstream's own pure
  shape in get_skylines), which touch no X-dependent stencil; and the full
  range brings basic-distance into the distances, exactly as upstream's pure
  estimate does, so staves land near their ideal separations rather than
  packed. When the alignment DOES have a system (nothing triggered it early),
  it stacks at the unpure minimum distances -- still a stand-in for EPG16's
  Page_layout_problem solution, recorded as such. Both stand-ins retire with
  EPG15 (pure reads in spacing) + EPG16 (the real solver).

  A visible side effect, deliberate: single-staff pages now sit with the
  system's top at y=0 (the alignment translates the staff down, then
  System::post_processing re-anchors), a RIGID vertical shift of the whole
  drawing relative to pre-EPG7 output. The comparator's inventory verdicts do
  not move.

LS-FIX3 -- THE FOUR LilyScheme GAPS EPG22's SWEEP MEASURED (2026-08-07)
-------------------------------------------------------------------------------

  All four fixes landed in CodeBrix.LilyScheme, not here; this block records what
  the PORT was doing wrong-by-proxy and what changed underneath it. The
  interpreter's own AGENT-README carries the mechanisms in full.

  1. define-method now extends a generic-capable PRIMITIVE GLOBALLY.

     lily/operators.scm specializes -, +, * and / on <Moment>, <Duration> and
     <Pitch>. LilyScheme was defining a fresh generic in the DEFINING module, so
     the extension was invisible from every other one -- and a parser scope
     evaluating (- pitch pitch) for \transpose resolved the raw numeric '-' and
     threw wrong-type-arg. 28 files in the EPG22 sweep, the whole accidental and
     \transpose family.

     Upstream's mechanism is not a module operation at all: oop/goops.scm's
     add-method! calls enable-primitive-generic! on the subr, which hangs the
     generic off the PRIMITIVE OBJECT. Every module shares that object, so the
     extension is global by construction. LilyScheme now does the same.

     NOT fixed by reordering LilyModules.Make. That was the tempting shortcut and
     the work order explicitly ruled it out: it diverges from ly_make_module
     shadowing for every binding, and it would not have made the extension global.

  2. GOOPS #:accessor carries a setter.

     scm/part-combiner.scm's (set! (split-index state) idx) expands to
     ((setter split-index) state idx). GOOPS's #:accessor makes an <accessor> --
     a generic whose setter is a generic -- but LilyScheme's define-class emitted
     a bare lambda, so `setter' threw wrong-type-arg: 28 files, the whole
     \partCombine family. The prelude now emits a make-procedure-with-setter.

     Measured before changing it: no caller anywhere in scm/ writes through the
     accessor's two-argument form, and no accessor name in scm/ is declared for
     two DIFFERENT slots, so the port's accessors did not also need to become
     generics. If a future upstream sync introduces either, that changes.

  3. Five unbound Guile-core names, all now in LilyScheme:
       ceiling-quotient (47 files), string-capitalize (22), substring/shared (7),
       mkdir (1), and ice9-format (1).

     floor-quotient was a SIXTH, hidden: lily-library.scm:1484 picks between
     ceiling-quotient and floor-quotient in one `if', so both arms evaluate as
     variable references and the log could only ever name the first. Counting
     from the log alone would have left it for the next sweep.

     ice9-format was not a missing procedure at all. scm/lily.scm opens with
     ((ice-9 format) #:select ((format . ice9-format))) and LilyScheme's
     use-modules dropped #:select's RENAMING form -- it took the module head and
     imported everything, which is a superset for bare selects and a silently
     unbound name for renamed ones. Renames are honoured now. The RESTRICTION
     still is not: scope stays wider than Guile's, never narrower, and narrowing
     it wants a session that can sweep behind the removal.

  4. finite? and euclidean-remainder MOVED out of Bootstrap/Epg8Callbacks.cs into
     LilyScheme's NumericPrimitives, where a Guile-core name belongs (EPG8's
     FINDINGS 3, carried by the EPG22 work order). They are DELETED here rather
     than duplicated: a copy would shadow the interpreter's own and re-create the
     divergence the move removes. The LilyScheme versions compute over that
     library's numeric tower instead of through this port's Rational, whose
     biased-by-one denominator is a documented trap.

     euclidean-remainder arrived with the floor/ceiling/truncate/euclidean
     quotient-remainder family, because Guile defines them as one family and the
     remainder is derived from the quotient so the division identity holds
     exactly. Guile's round-* and centered-* are deliberately absent: nothing in
     LilyPond names them, and an undemanded rounding rule is a parity bug waiting
     for its first caller.

    lyric-combine (EPG18)

  WHY THOSE FIVE WERE HELD BACK, and it is not arbitrary. Three of them are
  built on Repeat_styler (repeat-styler.cc, ~300 lines, an abstract base with
  null / segno / volta subclasses), and volta-specced reads volta_bracket_depth
  and volta_brackets_enabled OFF Alternative_sequence_iterator, which in turn
  needs the styler. Landing any one of them alone means writing a stand-in for
  exactly the machinery the group exists to port -- the kind of half-reproduced
  declaration this project's standing rule 4 is about. They go together, with
  the styler, in EPG17's next session.

  ONE NEW-IN-FAMILY FILE: Music/MusicFactory.cs, the managed stand-in for
  upstream's Lily::make_music / Lily::make_span_event.

  It exists because of a distinction that is easy to miss and silent when
  missed. Upstream announces events two different ways, and the port has to
  match each:

    send_stream_event (context, "GraceChange", origin)
        -> a Stream_event built directly. Port: Context.MakeEvent +
           SendStreamEvent. Grace_iterator uses this one.

    Lily::make_music (sym) ... ev->send_to_context (ctx)
        -> a MUSIC object built through Scheme's make-music, which reads
           scm/define-music-types.scm and initialises `name' and `types'.
           Port: MusicFactory.MakeMusic + MusicObject.SendToContext.
           Premeasure_iterator and Measure_remainder_iterator use this one.

  MusicObject.ToEvent derives the stream event's CLASS from `name'/`types'. A
  music object built with `new MusicObject' carries neither, so the event it
  becomes matches NO engraver's listener -- and nothing fails, because a
  broadcast nobody hears is silent by design. The first draft of these
  iterators took the Context.MakeEvent shortcut for all of them and would have
  shipped exactly that.

  FAITHFULNESS NOTES on the four:
  * Fine_iterator derives from Simple_music_iterator, NOT Event_iterator, and
    upstream says why: there are conditions under which it does not send its
    event (inside LyricCombineMusic) and complicating Event_iterator for them is
    not worth it. Kept as upstream has it.
  * Grace_iterator converts between two clocks -- the outside moment and the
    wrapped music's -- and announces GraceChange so Grace_engraver can tell
    \stemNeutral \grace { ... apart from \grace { \stemNeutral ... . The
    Grace_engraver that consumes it is NOT yet ported (still EPG17), so the
    event is currently announced to nobody. That is upstream's own ordering, not
    a gap: the iterator is correct on its own terms and the engraver is the next
    file in the same group.
  * Measure_remainder_iterator SKIPS its start event when the music has zero
    main length -- upstream's comment explains that it would otherwise try to
    set measureLength = 0 at a measure boundary, which is invalid and warns.
  * grace-music.cc's start callback returns a moment whose GRACE part is the
    negated total length and whose main part is zero. Getting the two parts the
    wrong way round is the classic Moment error and would place every grace note
    a whole note early instead of in grace time.

  * Lyric_extender::print calls Lily::unbroken_spanner_p, which is
    (eq? spanner (ly:grob-original spanner)) and nothing else. ly:grob-original
    answers the grob itself when it has no original, so the port tests
    Original == null directly rather than crossing into Scheme for a pointer
    comparison.

  * Vowel_transition reads bound-details through SchemeUtilities.Assq rather
    than a port of ly_assoc_get. Every key it looks up is a SYMBOL, for which
    upstream's assoc and assq agree exactly. Interval_t<Moment>::length () has
    no counterpart on MomentInterval, so its one call is written out as
    right - left, which is what that method is.

  * Melody_spanner::calc_neutral_stem_direction walks a SIGNED index with -1
    standing in for VPOS. Upstream's vsize is unsigned and the algorithm relies
    on TWO wraps -- last_nonneutral + 1 == 0 on the first pass, and
    last_nonneutral-- stepping 0 back to VPOS -- both of which are ordinary
    arithmetic on a signed index. The loop conditions are rewritten to match
    and nothing else about the walk changes. Fenced with hand-computed
    expectations in Epg18Tests, because a wrong answer here is a stem pointing
    the wrong way, not a missing glyph, and no sweep would isolate it.

  * The three lyric engravers' acknowledge_lyric_syllable (Grob_info_t<Item>)
    and Melody_engraver's acknowledge_stem / acknowledge_slur become interface
    tests at the top of one AcknowledgeGrob, since the port has no acknowledger
    macro layer. Same treatment as Tuplet_engraver's four.

  FAITHFULNESS NOTES:

  * Extender_engraver creates an auto-extender SPECULATIVELY and kills it when
    the next lyric event turns out not to be an underscore. That is upstream's
    design, not an accident of translation, and it is why
    pending_autoextender_melisma_busy_ exists and why the melisma test is
    delayed to stop_translation_timestep -- a melisma can start during the
    time step's own processing.

  * Extender_engraver and Hyphen_engraver deliberately do NOT use
    assign_event_once on the lyric and hyphen events they merely OBSERVE.
    Upstream says why in both files: the engraver that OWNS the event warns
    about conflicts, and warning twice about one input error is worse than not
    warning here at all.

  * Lyric_engraver treats a syllable whose text is a single SPACE as "hold the
    previous one": it prints nothing and re-aligns the PREVIOUS syllable by
    lyricMelismaAlignment. The comparison is against a Scheme string, so it
    goes through SchemeUtilities.IsEqual rather than a C# string compare.

  * get_current_note_head finds the head sounding NOW by walking busyGrobs and
    keeping the one whose recorded END equals now plus its own event's length.
    busyGrobs records only ends, so that arithmetic is upstream's way of asking
    "did this grob start here". Its own comment records that includeGraceNotes

  TWO DEFECTS IN ALREADY-PORTED CODE, both silent until EPG18 ran:

  1. THE BIG ONE — Music_iterator did not hold its context through a
     Context_handle, so EVERY CONTEXT IN THE SCORE READ AS REMOVABLE.

     Upstream's music-iterator.hh declares `Context_handle handle_;' and routes
     get_own_context/set_own_context through it. That is not bookkeeping: the
     handle's client count is exactly what makes Context::is_removable answer
     FALSE for a context an iterator is still reporting to. The port stored a
     plain `Context _context;' field, so client_count_ stayed 0 everywhere and
     a freshly created Voice — no children, no clients — reported itself
     removable while its own notes were still being iterated.

     Nothing failed loudly for four sessions because almost nothing ASKS.
     Lyric_combine_music_iterator::run_always is the first caller in the port
     to depend on the answer, and the consequence was total:

       run_always () = lyric_iter_ && lyric_iter_->ok ()
                       && !(music_context_ && music_context_->is_removable ())

     find_voice succeeded, set music_context_ to the Voice, the Voice reported
     itself removable, run_always went FALSE, and
     Simultaneous_music_iterator::create_contexts — which erases any child that
     is not ok () right after init_context — DELETED THE ENTIRE \lyricsto
     BRANCH before a single syllable was iterated. `\addlyrics' happened to
     survive because its generated wrapper kept the branch ok, which is why the
     two spellings behaved differently and why this looked like a \lyricsto
     parsing problem at first.

     Fixed in Translation/MusicIterator.cs: OwnContext now reads and writes
     through a ContextHandle. Context.CheckRemoval and everything else that
     consults IsRemovable now get upstream's answer. Expect this to move the
     sweep beyond lyrics — it changes when contexts die across the whole suite,
     which is what upstream intends.

  2. Grob did not implement IDiagnostics, though upstream declares
     `class Grob : public Smob<Grob>, public Diagnostics'. EPG22 added
     Warning/ProgrammingError/Origin to Grob as plain members and stopped
     there, so a grob had the diagnostic surface but not the TYPE: an
     `(IDiagnostics)' cast on a Spanner compiled and threw
     InvalidCastException at run time, which is how spanner-break-beyond-parent
     went SVG -> NOOUT the moment Hyphen_engraver warned about an unterminated
     hyphen. Same family as EPG17's finding that MusicObject did not implement
     it either. Fixed by declaring the interface on Grob and mapping
     IDiagnostics.Origin() to the existing Origin property.

  because number? is what the arithmetic layer tests.

  THE SCORER, AND THE ONE PLACE FAITHFULNESS NEEDED EXTRA WORK

  beam-quanting.cc is a scorer, so standing rule 2 applies: it is translated
  literally, including the several places where upstream computes a value it
  never uses (beam_width in init_instance_variables is the clearest). One point
  needed more than literal translation to STAY faithful, and it is worth
  understanding before touching this file.

  Upstream picks the winning configuration out of a std::priority_queue whose
  comparator inverts, so the top is the SMALLEST demerits. Beam quanting
  routinely produces configurations with EQUAL demerits -- symmetric music is
  the normal case, not the exotic one -- and which of those equal configurations
  comes off the queue IS the beam's final position on the page. std::priority_
  queue is not stable, and neither is System.Collections.Generic.PriorityQueue,
  but two unstable heaps do not have to break a tie the same way. Only the same
  heap does. ConfigurationHeap is therefore a direct replica of libstdc++'s
  push_heap / pop_heap / adjust_heap over a List, with upstream's comparator, so
  the sequence of pops is identical. Do not replace it with a library queue.

  A second, smaller trap in the same file: round_halfway_up is
  floor (x - 0.5) + 1.0, NOT floor (x + 0.5). Upstream says so in
  flower/libc-extension.cc and the two differ on exact .5 boundaries, which is
  precisely where a quant sits.

  BEAMING PATTERN COUNTS ARE UNSIGNED

  Beam counts in Translation/BeamingPattern.cs are uint, not int, and that is
  deliberate. beamify's third loop subtracts from a beam count:

    infos_[i].beam_count_drul_[opposite] -= max (count(i) - count(neighbor), 1u)

  guarded by count(i) >= count(neighbor). A stem with count 0 can still reach
  this, because the flag-direction CORRECTION loop assigns a non-CENTER
  direction to stems the first loop skipped. When it does, upstream computes
  0 - 1 in unsigned arithmetic and WRAPS, and every later comparison reads the
  wrapped value. Using int would quietly turn that into -1 and change which
  branch subdivide_beams takes. The port wraps where upstream wraps.

  BEAM PRINT EXTREME INDEX

  Beam::print computes

    vsize extreme = (segments[0].vertical_count_ == 0
                       ? segments[0].vertical_count_
                       : segments.back ().vertical_count_);

  and then INDEXES segments with it. vertical_count_ is a signed beam rank, and
  storing a negative one in a vsize is undefined behaviour upstream. In practice
  it evaluates to 0, because the segments are ordered by ascending vertical
  count so either the first is 0 or the last is. The port clamps the index into
  range rather than letting C# throw where C++ reads garbage: a faithful
  translation must not turn silent undefined behaviour into an exception.

  BEAM BOUNDS BEFORE LINE BREAKING

  Beam::print and Beam::calc_beam_segments both refine their common horizontal
  reference point with me->get_bound (d)->common_refpoint (...), with no null
  check. Upstream does not need one: Spanner::do_break_processing walks away
  from a spanner missing either bound, so such a spanner is never assigned to a
  system and never typeset. That guarantee lives in line breaking, which is
  EPG15/EPG16's, and the port reaches print for an unbounded beam -- it is what
  made tablature-slurs-with-beams and ten other files stop producing a page,
  and it is the regression the ratchet caught on this session's first sweep.
  Both walks go through Beam.CommonWithBound, which skips a missing bound. A
  beam with no bounds has no stems either, so it yields no segments and draws
  nothing, which is the same page upstream produces after calc_direction removes
  it. REVISIT WHEN EPG15/EPG16 LAND: the guard should become unnecessary.

  THE EPG6 BEAM SEAM IS RETIRED

  Objects/Stem.cs carried a private BeamHelpers class holding faithful copies of
  six beam.cc statics, pulled forward because their callers landed in EPG6 while
  beams were EPG10's. Beam.cs now owns all six under their upstream names, the
  Stem and StemTremolo call sites point at Beam, and BeamHelpers is deleted.

  THREE FREE FUNCTIONS THAT WERE NEVER CARRIED

  All three live in files whose ledger rows say `ported', and all three were
  found by porting a caller. Their rows stay `ported' -- the file was ported and
  the function was the gap. This is the fourth session running to find some of
  these; budget for it.

    Grob::pure_relative_y_coordinate (grob.cc) and the free function
    call_pure_function (grob-property.cc) that it needs. Beam::consider_auto_knees
    is the caller. call_pure_function has semantics worth reading: an unpure-pure
    container whose pure half is OMITTED answers through its unpure half, but a
    BARE procedure answers #f rather than being called, because calling it would
    not be pure.

    Grob::spanned_column_rank_interval (grob.cc, item.cc, spanner.cc) and
    Grob::less (grob.cc). Beam_collision_engraver::finalize walks beams and
    covered grobs in parallel in horizontal order and needs both.

    Engraver::announce_grob (inf, ctx), announce_end_grob (inf, ctx),
    announce_grob_locally_only and announce_end_grob_locally_only
    (engraver.cc). Auto_beam_engraver announces its beam LOCALLY and then again
    in the context the beam started in, which may no longer be its own by the
    time the beam ends.

  TWO LilyScheme GAPS, BOTH MEASURED

  Neither is a beam bug; both are Guile-compatibility gaps that no earlier group
  had reached. Fenced by NaryEqualityTests in the LilyScheme repo.

    eq?, eqv? and equal? are declared SCM_DEFINE (..., 0, 2, 1) in
    libguile/eq.c -- ZERO required arguments, two optional and a rest -- so they
    are N-ARY: fewer than two arguments answer #t, and longer lists compare
    ADJACENT pairs. LilyScheme fixed them at exactly two. ly:beam::calc-knee
    decides whether a beam is kneed with (apply eqv? <one stem direction per
    stem>), so EVERY beam died on wrong-number-of-args, including the four
    eighth notes of { c'8 c'8 c'8 c'8 }.

    member and assoc take an OPTIONAL equality predicate, called in the caller's
    own argument order as (predicate key element). LilyPond's
    default-auto-beam-check finds a beat setting with (assoc type sorted-alist
    <=). Guile's C assoc is two-argument; the three-argument form comes from
    SRFI-1, which the port resolves through the core binding, so the core one
    now accepts it. Scope stays WIDER than Guile's here, never narrower, which
    is the same posture LS-FIX3 recorded for #:select.

  WHAT BEAMS STILL DO NOT DO, AND WHY IT IS NOT THIS GROUP'S

  Beams draw with correct thickness and correct beam counts, and the polygon
  count matches the oracle file for file. They are close to ZERO LENGTH in most
  swept files, because a beam segment runs from one stem's x to another's and
  the port's columns are still at x = 0 in most files -- EPG4 measured 108 of
  915 files placing at real x, and that has not moved. When EPG15/EPG16 land the
  real line-breaking and spacing pipeline, beam length follows without further
  work here. Nothing in this group papers over it.

  SINGLE-STEM CHORD TREMOLO BEAMS

  Chord_tremolo_engraver gives a stem its `beaming' only when a PREVIOUS stem
  exists, so the first stem of a tremolo group is beamless until the second
  arrives. In five places in the sweep the port ends up with a tremolo Beam
  holding exactly ONE stem, and that stem's beaming is '(). Upstream's
  Beam::calc_beam_segments then reads scm_car of the empty list; upstream's own
  Beam::calc_beaming, one function earlier, guards the identical data with
  `if (scm_is_pair (this_beaming))', so the port applies that same guard at the
  sibling site and the stem contributes no segments -- which is correct, since
  beaming is exactly what says where a stem's segments are.

  That is the SYMPTOM, and it is fixed. The CAUSE -- why the port produces a
  one-stem tremolo beam where upstream evidently produces a two-stem one -- was
  measured but not chased down: it shows up only in the full sweep and not when
  the file is run alone (whole-note-tremolo-direction.ly is the one that caught
  it, and it is the last regression the ratchet reported this session). The
  suspects are the tremolo engraver's span-stop handling and the sweep's known
  cross-file state leak; distinguishing them wants a session that owns tremolo
  work. Left for EPG20 or Phase 4, recorded here rather than in a comment so it
  is findable.

WHAT THE ALREADY-PORTED FILES HAD NEVER CARRIED
--------------------------------------------------------------------------------

FIVE gaps in files whose ledger rows have said `ported' since EPG0. All five are
the same shape, and it is the shape standing rule 4 describes: something upstream
declares was half-reproduced, and NOTHING FAILED.

THE HEADLINE ONE IS NOT A TIE OR A SLUR DEFECT AT ALL, AND IT AFFECTED EVERY
GROB IN EVERY SCORE.

  0. lily/grob.cc's CONSTRUCTOR installs four DEFAULT callbacks on any grob whose
     description does not name them:

         if (scm_is_null (get_property_data (this, "X-extent")))
           set_property (this, "X-extent", Grob::stencil_width_proc);
         if (scm_is_null (get_property_data (this, "Y-extent")))         ...
         if (scm_is_null (get_property_data (this, "vertical-skylines"))) ...
         if (scm_is_null (get_property_data (this, "horizontal-skylines"))) ...

     The port's constructor stopped after the meta/interfaces/object-callbacks
     block and installed none of them. Every one of the four procedures was
     REGISTERED and working; only the defaulting was missing, which is why no
     unbound-name warning ever appeared.

     What it cost: most grobs name X-extent and Y-extent explicitly in
     scm/define-grobs.scm, so most were unaffected. NoteHead does not name
     X-extent. So every note head in every score the port has ever engraved has
     been answering an EMPTY horizontal extent, and the empty answer was CACHED
     the first time anything asked.

     Nothing asked, for eleven groups. Horizontal spacing goes through
     NoteColumn's own extent callbacks; beams measure stems; lyrics measure
     syllables. Tie_formatting_problem is the first code in the engine to ask a
     NOTE HEAD for its width -- and it feeds the answer straight into a Skyline,
     where an empty interval turns into a NaN roof height and the whole page
     dies. That is how a defect this size stayed invisible: it needed a caller
     that both wanted the value AND could not survive a wrong one.

     Found by the ratchet, not by reading: EPG11's first sweep reported 23
     regressions, all of them semi-tie files, all with the same
     "Skyline building slope is not finite".

The other four are the ordinary kind -- ties and slurs are simply the only
callers anywhere in the engine, and neither existed until now.

  1. lily/misc.cc's peak_around and convex_amplifier, and misc.hh's inline
     linear_interpolate and normalize. These are the two penalty CURVES the tie
     and slur scorers charge every demerit through, plus the two interpolators.
     Now in Objects/Misc.cs.

     A fifth thing came out of the same look: Layout/StencilIntegral.cs had its
     own PRIVATE copy of linear_interpolate, associated as
     ((x2-x) y1 + (x-x1) y2) / (x2-x1) where upstream's misc.hh writes
     (x2-x)/(x2-x1) y1 + (x-x1)/(x2-x1) y2. Algebraically identical, not

  2. lily/axis-group-interface.cc's staff_extent. One caller in the whole engine:

TWO PIECES OF DEAD CODE, REPRODUCED DEAD
--------------------------------------------------------------------------------

Both are cases where the faithful port is the one that does nothing, and where
"fixing" it would add behaviour upstream does not have. Recorded because a later
reader will otherwise find them and file a bug.

  * Tie_column::before_line_breaking. Its whole body is a loop over
    `get_property (me, "ties")'. But `ties' is written by
    Pointer_group_interface::add_grob, which goes through set_object -- a
    DIFFERENT alist on the grob from the one get_property reads. The property
    read therefore answers the empty list, the loop never executes, and the
    callback is a no-op that upstream nonetheless registers on TieColumn.

    Making it read the OBJECT would start moving the column's bounds. Upstream
    never does that, so the port does not either.

  * Tie_formatting_problem::generate_collision_variations' last branch, guarded
    by `i == ties.size ()' inside a loop bounded by `i < ties.size ()'. It cannot
    hold. Reproduced unreachable; making it live would add a candidate variation
    that upstream never scores.

  * A third, milder one, in Slur_engraver: upstream registers an acknowledger for
    `fingering-interface', and nothing in scm/ or lily/ declares that interface.
    The acknowledger is dead upstream and dead here. Kept rather than dropped, so

DELIBERATE DIVERGENCES
--------------------------------------------------------------------------------

  * VALUE SEMANTICS WRITTEN OUT. Upstream's Tie_configuration lives inside a
    std::vector, so `Ties_configuration variant (base)' deep-copies, and every
    push_back and every assignment from the possibilities_ cache copies too. The
    port makes it a class, which shares. Every one of those copies is an explicit
    Copy() here, and nothing from the cache is ever aliased into a
    Ties_configuration -- because if one ever were, one variant's demerits would
    leak into another and the 1-opt search would compare candidates to a moving
    target. Two tests fence it directly (Epg11Tests).

    One place upstream deliberately mutates the CACHED configuration before
    copying it -- generate_ties_configuration's manual delta_y -- and the port
    reproduces that too, mutation and all.

  * BEZIER COPIES. avoid_staff_line and fit_factor take Bezier BY VALUE upstream
    and then translate, rotate and scale it. The port's Bezier is a class, so both
    Copy() first. Without that, fit_factor would deform the caller's curve, which
    is the curve generate_curve keeps and Slur::print draws. Fenced by
    Epg12Tests.fit_factor_does_not_deform_the_curve_it_measures.

  * EMPTY BOXES. Upstream's Box default constructor leaves both intervals EMPTY;
    C#'s default(Box) is a point at the origin. Every std::map entry upstream
    default-inserts on first touch (stem_extents_, head_extents_) is therefore
    created explicitly empty in the port. Getting this wrong would silently unite
    a real extent with a phantom point at zero, which is the kind of error that
    moves a tie by a fraction of a staff space and never throws.

  * THE CONFIGURATION HEAP IS SHARED, NOT RE-DERIVED. EPG10 wrote a replica of
    libstdc++'s push_heap/pop_heap privately inside BeamQuanting.cs.
    Slur_score_state::get_best_curve runs the identical pattern with the identical
    inverting comparator, so the replica moved to Objects/ConfigurationHeap.cs and
    both scorers use it. The algorithm is unchanged; beams break equal-demerit
    ties exactly as they did before. The reason it is a replica at all is
    unchanged too: a heap is not a sort, equal scores are the NORMAL case in
    symmetric music, and which of two equal candidates ends up on top is where the
    beam or slur ends up.

  * round_halfway_up MOVED to Flower's LibcExtension, which is the file upstream
    declares it in, once ties and slurs added three more callers to beams' one.
    Arithmetic unchanged: floor (x - 0.5) + 1.0.

  * THE SLUR'S SEARCH RANGE IS GUARDED AGAINST A COLLAPSED HORIZONTAL SPAN, and
    this is the same divergence EPG17 recorded for Bracket::make_bracket.
    Slur_score_state::fill widens the range of endpoint heights it will explore by
    interpolating ALONG the slur, which divides by (right base attachment X - left
    base attachment X). Upstream may do that unguarded because horizontal spacing
    has always run by the time a slur is scored, so a slur's two ends are staff
    spaces apart. This port scores slurs while spacing is incomplete and most
    columns still sit at x = 0.

    On phrasing-slur-tuplet the two ends came out 0.037 apart. The division did not
    produce an infinity -- it produced a search range of +-5455 staff spaces where
    upstream's is +-4. enumerate_attachments then stepped half a staff space at a
    time across that range, twice nested: about 119 MILLION configurations, each
    allocated and each about to be scored. It reads as a hang, and it hung the
    sweep for as long as it was left running.

    Guarded at upstream's OWN threshold for a slur too short to treat as one --
    `minimum-length', which enumerate_attachments already uses to decide that a
    candidate should re-attach to the note head centres instead. Below that span
    there is no "along the slur" to interpolate and an encompassed object
    contributes nothing to the range. A second, narrower guard rejects a
    non-finite contribution outright. Whenever the span is real, the expression is
    upstream's, unchanged. REVISIT WHEN EPG15/EPG16 LAND.

    Worth stating plainly for whoever picks this up: the underlying condition is
    NOT a slur bug. It is EPG4's recorded state -- columns leave x = 0 in only
    some files -- meeting the first code in the engine that divides by a
    horizontal distance between two note heads.

  * PURE HEIGHTS ARE APPROXIMATE UNTIL EPG15. Grob::pure_y_extent is ported, but
    it reads Y-extent through the port's minimal pure stand-in rather than through
    unpure-pure-container.cc's call_pure_function, which is EPG15's. A grob with a
    genuine pure callback is therefore measured by its ordinary extent. This
    matters only during line breaking, which is EPG15's too, so the approximation
    and the code that would expose it land in the same session. REVISIT AT EPG15.

  * SORT STABILITY. Tie_column and Semi_tie_column sort their ties with
    std::sort on Tie::less / Semi_tie::less, which is unstable; List<T>.Sort is
    also unstable but not identically so, so two ties at the SAME staff position
    could order differently from upstream. In a tie column the ties attach to
    distinct note heads of one chord, so equal positions do not arise in practice.
    Recorded rather than solved: replicating libstdc++'s introsort is a far larger
    undertaking than replicating its heap, and unlike the heap there is no known
    case where it bites.

  * SCORE CARDS ROUND DIFFERENTLY. The debug annotation strings format demerits
    with "F2", which rounds halves away from zero where C's %.2f rounds to even.
    Debug-only: the cards are written to a grob's `annotation' property solely
    when debug-tie-scoring / debug-slur-scoring is on, and never reach a parity
    page.

ORDINARY TIES DO NOT DRAW, AND THE REASON IS IN THE PARSER
--------------------------------------------------------------------------------

Measured against the oracle's own references on 2026-08-08, counting the curves
each page carries:

    repeat-tie            port 5    oracle 5     EXACT MATCH
    laissez-vibrer-ties   port 22   oracle 22    EXACT MATCH
    slur-broken-trend     port 20   oracle 30    draws; broken curves await EPG15
    tie-accidental        port 0    oracle 1     ORDINARY TIES DO NOT DRAW

The two semi-tie families are not merely working, they AGREE WITH THE ORACLE
EXACTLY -- and a laissez-vibrer tie goes through the same Tie_formatting_problem,
the same scorer, the same Tie::get_control_points and the same Tie::print as an
ordinary tie. Everything EPG11 owns downstream of the event is therefore verified.

The gap is upstream of the engraver. Instrumented: Tie_engraver IS instantiated,
IS acknowledging every note head, its listener NEVER fires, and the note event's
`articulations' list arrives EMPTY.

`~' is not a grammar token. There is no `~' rule in upstream's parser.yy or
lexer.ll; upstream binds it in ly/declarations-init.ly as a STRING-NAMED
identifier:

    "~" = #(make-music 'TieEvent)

and the port's parser does not resolve string-named identifiers, so no tie-event
is ever created and nothing hears one.

THAT IS A TRACK P GAP, not an EPG11 one, and Track P is marked COMPLETE. Recorded
here rather than fixed because the parser is a different track. Four end-to-end
tests in TiesAndSlursEndToEndTests are skipped with this reason in their skip
message -- the CONTROL included, because a control that would pass for the wrong
reason is worse than one that does not run. Unskip all four together when the
parser resolves "~".

  Instrument_switch_engraver's stop_translation_time_step -- REPRODUCED DEAD

    Upstream declares and defines `stop_translation_time_step', with an extra
    underscore, where all 91 other engravers spell it
    `stop_translation_timestep'. That is not the name the translator framework

    Upstream's Grob_scripts_map is std::unordered_map, whose iteration order is
    unspecified. The port keeps a Dictionary keyed by reference identity and
    walks it in INSERTION order. This cannot change output: each bucket is
    ordered independently of every other, so the order the buckets are visited
    in is not observable.

  Three stable sorts where upstream uses std::sort -- DELIBERATE

    std::sort is not stable. Script_column::order_grobs, Fingering_column's
    offset sort and New_fingering_engraver's Finger_tuple sort all feed
    decisions where the tie-break is visible: which fingering goes up and which
    goes down when a chord is split, and which of two flush fingerings moves.
    An unstable tie there is a coin flip a second implementation cannot
    reproduce, so the port sorts stably. (scm_stable_sort_x, which
    Script_column::order_grobs actually calls, is stable upstream too.)

    already records. Skipping it can only leave a staff ALIVE that upstream

  Line_spanner::calc_bound_info's assert

    Upstream asserts extreme_bound_groups_there[dir] is non-null. An assert is

  DEFECTS FOUND IN ALREADY-PORTED CODE

  1. lily-guile.cc's ly_assoc -- assq COMPARED BOXED NUMBERS BY REFERENCE

     THE BIGGEST OF THEM, and it was silent. Guile fixnums, booleans and
     characters are IMMEDIATES, not heap objects, so (eq? 1 1) is true and
     (assq 1 '((1 . a))) finds its entry. SchemeUtilities.Assq compared with

RATCHET-FIX 2026-08-08 -- THE THREE ROWS EPG14 LEFT OPEN
-------------------------------------------------------------------------------

  EPG14 closed with the ratchet gate RED on three rows and left them for a
  ruling rather than re-baselining them. All three were diagnosed to root this
  session; two were defects and are FIXED, and the third is a dependency on
  work EPG15/EPG16 owns and is recorded here rather than papered over.


  THE TOPLEVEL \layout BLOCK NEVER REACHED ANY CONTEXT (script-custom-definition)

  This is the largest of the three and it was NOT what the file's error message
  said. The reported failure was (zero? '()) inside
  horizontal-script::calc-staff-position, reading an unset `side-axis'. That is
  a SYMPTOM two layers down: side-axis is not a Script grob default -- 
  scm/define-grobs.scm says "'padding, 'side-axis set in script definitions" --
  so it can only arrive from the scriptDefinitions alist, and the file's alist
  was never reaching the engraver at all. The warning that gave it away was
  "do not know how to interpret articulation: segno-coda", six times.

  THE DEFECT, and it is a whole mechanism rather than one property: NO property
  operation written in a toplevel \layout block had ANY effect, for the entire
  life of the batch runner. Neither an \override nor a plain assignment.

  It survived this long because it splits exactly in half, and the visible half
  works. A \layout { \context { ... } } block's TRANSLATOR list was applied
  correctly -- \consists really does add an engraver -- because a translator
  list is read off the ContextDef the block built. Property operations are not:
  they are applied by Context_def::apply_default_property_operations against
  whatever definition find_context_def answers with, and that lookup goes
  through the OUTPUT DEF. Any probe written with \consists reports the block
  working.

  Root cause: parser.yy's toplevel_expression REBINDS the $defaultlayout
  IDENTIFIER to the definition a toplevel \layout builds; it does not mutate
  the one already there. Upstream therefore resolves the layout BY NAME, late --
  print-book-with (scm/lily-library.scm) does (ly:parser-lookup '$defaultlayout)
  at book-processing time and hands the answer to ly:book-process. BatchRunner
  captured LilyPondInit.DefaultLayout(), the cached init-layer OBJECT, before
  the parse, so it always engraved under the pristine layout and every toplevel
  \layout in the suite was silently discarded.

  Fixed by resolving the identifier where upstream resolves it: inside the book
  handler, after the parse, falling back to the cached object when the
  identifier names nothing. ScoreLayout's own preference is unchanged -- a
  score's own \layout block still wins -- and needs no change, because
  get_layout (lily-parser.cc) opens every \layout head by CLONING whatever
  $defaultlayout names at that moment, so a score block already inherits the
  toplevel one and can then override it.

  This is EPG13's $defaultpaper finding one identifier over, and it is the same
  lesson twice: these definitions are reached BY NAME and rebound wholesale, so
  a cached reference to the object is not a reference to the current value.
  Fenced by ToplevelLayoutEndToEndTests, whose every case is paired against the
  same operation written in the music -- a path that never went through
  $defaultlayout and so always worked.


  slashed-beam -- NOT FIXED, AND THE REASON IS EPG15/EPG16

  Reported as "(min) called with zero arguments". Traced to
  beam::calc-right-extreme-vertical-count in scm/output-lib.scm, which filters
  a kneed beam's beam-segments down to those touching the right end of the beam
  and then does (apply min <their vertical counts>). The filter comes back
  EMPTY, so min is applied to '().

  Measured on the file's own kneed beams: the stems of the failing beams sit at
  only TWO distinct x-coordinates -- 1.2392 and 0.065 -- and they run BACKWARDS,
  later stems at smaller x. Four notes, two positions, wrong order. That makes
  the segments' horizontal intervals INVERTED, e.g. (1.1742 . 0.13), and an
  inverted interval is is_empty() by Interval's own definition, so
  Beam::calc_x_positions falls into its own "beams without segments" fallback
  and sets both ends to the same coordinate. X-positions comes out
  (1.2392 . 1.2392) and nothing can match it.

  The port's Beam::calc_x_positions is upstream's, line for line, INCLUDING
  that fallback -- upstream fed the same segments would answer the same thing.
  The divergence is upstream of all of it: the columns have not been placed, so
  the stem coordinates are not yet meaningful. That is EPG15/EPG16.

  This is the FOURTH instance of one recorded pattern and it is worth naming as
  such: EPG10 (beams draw with correct count but near-zero length), EPG12 (the
  slur search range explodes when the horizontal span collapses -- "upstream may
  do that unguarded because spacing has ALWAYS run by then"), EPG17
  (Bracket::make_bracket divides by the bracket length), and now this. The
  earlier three were in C++ and could be guarded at upstream's own threshold.
  This one CANNOT be: the arithmetic is in scm/output-lib.scm, which is vendored
  byte-identical, and editing vendored upstream Scheme to survive a condition
  upstream never meets would be a parity bug wearing a fix's clothes.

  Why the file regressed at EPG14 rather than earlier: EPG14 fixed
  value_type_check refusing a procedure for a grob property, which is what had
  been silently throwing away \override Beam.stencil = #beam::slashed-stencil.
  Verified directly -- the same music with the stencil override removed still
  produces a page. Before EPG14 the default beam stencil drew and the file
  passed; EPG14 made the override real, and the code it now reaches needs
  spacing to have run.


  THREE MORE DEFECTS THE \layout FIX UNCOVERED

  Turning toplevel \layout blocks on ran machinery that had never executed, and the
  ratchet caught the consequences twice. All three were pre-existing; none is a cost
  of the fix.

  (1) equal? NEVER REACHED A HOST OBJECT'S EQUALITY HANDLER (LilyScheme).

  scm_equal_p ends by dispatching to a smob's equal_p; LilyScheme's SchemeEqual handled
  pairs, strings and vectors and then answered #f. LilyPond's moment<=? is
  (or (equal? a b) (ly:moment<? a b)), so "is this moment at or before that one"
  answered NO at the one moment they are the SAME. Measured directly: measurePosition
  printed as 0 while (moment<=? measurePosition ZERO-MOMENT) was #f.

  Measure_spanner_engraver therefore never cleared its finished spanner at
  stop-translation-timestep and fell through to its finalize branch -- which is
  scm/scheme-engravers.scm:306, (set! (ly:spanner-bound finished RIGHT) ...), an
  UPSTREAM bug: ly:spanner-bound is a plain LY_DEFINE with no setter half. Upstream
  never reaches it. This is EPG14's assq-compares-boxed-numbers-by-reference finding
  one level up.

  Fixed with ISchemeEqual, the managed analogue of declaring an equal_p, on the model
  of IApplicable. The roster was READ OUT of the pinned source rather than guessed:
  exactly eight types declare a handler -- Duration, Moment, Listener, Input, Pitch,
  Tuplet_description, Prob and Spring. Spring's is literally scm_is_eq, so identity is
  already correct for it. Six are implemented, each delegating to an Equals override
  that was verified field-for-field against upstream's equal_p. PROB IS NOT: its
  handler is a real algorithm (it skips `origin' fields, compares class names, and
  walks both property alists), nothing measured demands it, and a half-right comparison
  would be worse than a recorded absence. OWED.

  The hook is opt-in on BOTH sides, matching Guile: a smob with no handler falls back
  to eq?, so implementing ISchemeEqual on a type whose upstream counterpart has none
  would answer #t where upstream answers #f.

  (2) A STALE UNIMPLEMENTED-THROW IN Measure_spanner::print.

  The bracket half threw, loudly and by name, saying it needed
  Bracket::make_axis_constrained_bracket "owed by EPG14". EPG17 landed lily/bracket.cc
  WHOLE -- that function included -- while pulling it forward for its own two bracket
  grobs, and the throw was never taken back down. Nothing demanded it in between
  because the \layout block that turns Measure_spanner_engraver on was being discarded.
  Wired to the existing Bracket.MakeAxisConstrainedBracket; measure-spanner.cc's ledger
  row now reads WHOLE. Worth generalising: a named absence stops being true the moment
  its owner lands, and nothing re-checks it.

  (3) \language LEAKS ACROSS FILES IN THE BATCH RUNNER -- THE THIRD PER-FILE LEAK.

  ly:parser-set-note-names rebinds (lily)'s `pitchnames', which is SESSION state, and
  RestoreDefaults did not put it back. One regression file, midi-key-signature.ly,
  includes arabic.ly, whose first line is \language "italiano" -- so every file swept
  after it parsed with ITALIAN note names.

  This one had been costing real rows since well before the \layout work, and the
  sweep logs prove it rather than the directory: at EPG14 part-combine.ly and
  part-combine-relative.ly were already NOOUT on "not a note name: g", while
  part-combine-a2.ly and part-combine-inside-scale-durations.ly still PRODUCED PAGES --
  with 12 and 26 parse errors respectively. A file whose notes fail to parse still
  yields a page, just an emptier one, which is exactly how a leak this large stayed
  invisible. All four now produce pages with ZERO parse errors.

  It is the same shape as the other two per-file leaks and belongs beside them:
  \paper mutates in place, set-global-staff-size rebinds $defaultpaper, a toplevel
  \layout rebinds $defaultlayout, and \language rebinds pitchnames. Upstream needs
  none of it -- one file per process. Fenced by BatchRunnerTests.

  THE EPG4 TRAP IS STILL LIVE, and it cost a bisect here: part-combine-a2.ly PASSES
  WHEN RUN ALONE and fails only inside the sweep. Bisecting the ordinal file list
  against the single victim found the culprit in nine runs; that is the technique to
  reach for, rather than a one-file probe, whenever a failure will not reproduce alone.


  (4) Context::check_removal WAS NEVER CALLED -- the deepest of the four.

  The port's Context.CheckRemoval is a faithful translation of upstream's
  check_removal, and NOTHING INVOKED IT. Upstream drives it from
  Global_context::run_iterator_on_me twice -- at the end of every timestep, right after
  apply_finalizations, and again after the iterator quits -- and both calls were absent
  from the port's loop.

  check_removal is what SENDS RemoveContext. So the port had the event defined, its
  listener registration wired, and the event never once fired. This is EPG18's
  Context_handle finding's sibling: same subsystem, same shape -- something declared

  MEASURED AGAINST THE ORACLE, not reasoned about -- and that mattered, because reading

All 30 upstream files ported, with NO pull-forward of any other group's FILES. One

Scope is D27's: MIDI GENERATION plus the comparator and the oracle's references.
MIDI PLAYBACK is out of scope for LilyPort entirely and nothing here plays anything.


THE ONE STRUCTURAL DIVERGENCE, AND IT IS NOT OPTIONAL: byte[] REPLACES std::string

  Upstream's Midi_item::to_string and every to_string below it answer a std::string
  that is A BYTE CONTAINER. A 0x90 status byte and a UTF-8 lyric live in the same
  type and are concatenated without conversion, and the result is written to a file
  descriptor unchanged.

  System.String cannot do that. It is UTF-16, so a MIDI payload assembled as a string
  must choose an encoding on the way out, and no single choice is right for both a
  status byte in 0x80-0xFF (which wants Latin-1) and a lyric (which wants UTF-8).
  The whole MIDI layer is therefore byte[] end to end: MidiItem.ToBytes,
  MidiChunk.ToBytes, MidiEvent.ToBytes, MidiStream.Write.

  THIS IS THE ONE PLACE IN EPG19 WHERE FOLLOWING THE LETTER OF UPSTREAM WOULD HAVE
  PRODUCED WRONG FILES RATHER THAN MERELY DIFFERENT CODE. Midi_text::to_string writes
  a variable-length LENGTH PREFIX taken from text_string_.length (), which is a BYTE
  count because a std::string already holds encoded bytes. A .NET string's Length is
  UTF-16 units, so every non-ASCII lyric would have been given a short length and
  silently truncated -- a file that still parses. Epg19Tests fences it with "é": one
  char, two bytes, and the prefix must read two.

  Flower gained BigEndianBytesU16/24/32 and HexToBytes for this. The existing
  char-based BigEndianU16/24/32 are untouched and keep their tests.


A DEFECT IN ALREADY-PORTED CODE, AND IT IS THE ONE TO REMEMBER:
Rational.FromDouble WAS THE ALGORITHM UPSTREAM EXPLICITLY WARNS AGAINST

  flower/rational.cc's Rational (double) is deliberately LOSSY: frexp, then twenty
  bits of mantissa (FACT = 1 << 20), normalize, apply the exponent as a shift,
  normalize again. Upstream comments on it directly:

      do not blindly substitute by libg++ code, since that uses
      arbitrary-size integers.  The rationals would overflow too easily.

  The port's FromDouble built the EXACT dyadic rational with BigInteger -- precisely
  the substitution that comment forbids -- and it overflowed exactly as predicted. A
  tempo ramp in the MIDI subsuite produced a double whose exact numerator does not fit
  a ulong; the conversion THREW; the exception escaped mid-write; and ELEVEN MIDI
  FILES were left truncated after their header, which the comparator reported as a
  verdict class of its own (UNPARSEABLE, the same class EPG17 met from ly:wide-char->utf-8).

  Corrected to upstream's algorithm. ONE deliberate divergence remains: where the
  exponent shift would exceed 63 bits upstream shifts a uint64_t past its width, which
  is UNDEFINED BEHAVIOUR in C++; the port saturates to zero or the signed infinity --
  the mathematical limit, and a defined answer where upstream has none.

  BLAST RADIUS, MEASURED RATHER THAN ASSUMED: the closing sweep is byte-identical to
  the opening one (1,856 SVG / 281 NOOUT / 9 ERROR) and the ratchet reports 0
  regressions and 0 improvements. Musical durations are dyadic and small, so they
  survive the lossy path exactly; that is why nothing on the layout side moved.


THE FIFTH PER-FILE LEAK, AND IT IS THE OLDEST AND WIDEST FOUND SO FAR

  Lily_parser::default_duration_ is what a note with NO written duration inherits.
  Upstream makes ONE PARSER PER FILE, so every file starts at a quarter note. The port
  runs one session across the whole sweep, and nothing put it back -- so file N's last
  written duration became file N+1's default. A file that writes no durations at all
  writes nothing to correct it, so the error persisted for as long as the run did.

  It now sits beside its four siblings in LilyPondInit.RestoreDefaults:
      \paper mutates in place
      set-global-staff-size rebinds $defaultpaper
      a toplevel \layout rebinds $defaultlayout
      \language rebinds pitchnames
      the parser remembers default_duration_ (and default_tremolo_type_)

  FOUND THROUGH MIDI, WHICH IS WHY IT SURVIVED TRACK P, EPG3, EPG4, EPG13 AND EVERY
  SWEEP SINCE. The layout comparator grades GLYPH INVENTORIES, and a page whose notes
  are all half length holds the same glyphs in the same order -- it is graded
  GLYPHS-DIFFER either way, for reasons that have nothing to do with duration. The MIDI
  comparator grades TICKS, and a note-off at 192 where the oracle says 384 is not a
  near miss. Measured both ways, and it is the EPG4 trap in reverse:
  crescendo-return-crescendo.ly is CORRECT when run alone and halved inside the sweep.

  Worth generalising: a comparator can only catch what it grades. The layout ratchet
  has been blind to every timing error in the suite since it was seeded.


DELIBERATE DIVERGENCES (EPG19)

    for the reason Translator::finalize became FinalizeTranslation -- Finalize is the
    C# destructor.

    order, which is at least reproducible.

    VERBATIM upstream (it is copied and pasted between the two files). The port

A SILENT DEFECT THE PORT ALMOST SHIPPED, AND THE GENERAL LESSON

  Upstream reads numeric context properties with from_scm<Rational>. The obvious C#
  spelling is `GetProperty (...) is Rational', and it looks like it says the same
  thing. It does not: an exact Scheme ratio such as performer-init.ly's
  `tempoWholesPerMinute = #60/4' arrives as a LilyScheme Ratio, and an integer as a
  long, so the test misses both and the fallback wins. The symptom was a tempo span
  opening at MINUS INFINITY and every tempo in the subsuite computed over an infinite
  interval.

  SchemeConvert.TryToRational was added for this and every numeric property read in
  EPG19 goes through it. Prefer it over a type test anywhere upstream writes
  from_scm<Rational>. Note that the pre-existing SchemeConvert.IsNumber does NOT count
  a flower Rational and is therefore not a substitute.

STATE THAT CAN LEAK, AND THE GUARD ADDED FOR IT

  Staff_performer keeps its instrument-to-channel map in STATIC members. Upstream's
  own mechanism -- the last Staff_performer to finalize clears them -- is reproduced
  faithfully, and StaffPerformer.ResetStaticChannelState was added for
  LilyPondInit.RestoreDefaults to call, because a score that dies before finalize would
  otherwise hand its channel assignments to the next file in the sweep. Upstream's own
  comment says these members "would prefer to be members of the containing class
  Performance"; this is that wish, minus the restructuring.

WHERE MIDI OUTPUT COMES FROM, AND WHAT STILL WAITS ON EPG16

  write-performances-midis -- and that is reached through ly:book-process, which the
  port does not take (D20's score-level short-circuit). LilyPortPerformer is therefore
  the MIDI twin of LilyPortEngraver and BatchRunner drives both, per score, writing
  <base>.midi and <base>-<n>.midi exactly as write-performances-midis names them so the
  comparator can pair candidate to reference by name alone. When EPG16 moves the runner
  onto the real book path, both collapse into it.

  The MIDI half is a SEPARATE try/catch from the engraving half, deliberately:
  upstream produces a page and a .midi from the same score independently, so a score
  whose layout fails must still be able to perform. Folding them together would make
  every MIDI reference hostage to a layout gap that has nothing to do with it.

DELIBERATE DIVERGENCES

  Figure_group is a CLASS, not a struct (figured-bass-engraver.cc)
                 Upstream's is a value type held in a std::vector, and every use in
                 the file mutates a group IN PLACE through a reference:
                 `Figure_group &group = groups_[i];`. A C# struct in a List<T> hands
                 back a COPY, so every one of those mutations -- the continuation
                 line, the figure item, the six figure fields -- would be written to a
                 temporary and silently dropped. This is the one translation error
                 this file makes easy, and it would not have failed loudly: the page
                 would simply have had no extenders.

  derived_mark() is not carried (figured-bass-engraver.cc, fretboard-engraver.cc)
                 Both exist only to keep SCM members alive across a Guile garbage
                 collection. Managed fields need no such help, and the methods have no
                 other effect.

  the arrow glyph name uses the invariant culture (arpeggio.cc)
                 Upstream builds "scripts.arpeggio.arrow." + std::to_string (dir).
                 A culture whose negative sign is not U+002D would build a name the
                 font does not contain, and a missing glyph is SILENT here -- the
                 arpeggio would simply lose its arrowhead.

  the string/fret/finger list is walked ONCE (tab-note-heads-engraver.cc)
                 Upstream calls scm_list_ref inside the loop, which is quadratic in
                 the number of strings. The port walks with a cursor. Visiting order
                 and values are identical; only the cost differs, and the index i is
                 still tracked because `index` is computed from it.

  a zero-height squiggle cannot spin the arpeggio loop (arpeggio.cc)
                 Arpeggio::print stacks squiggles until they cover the chord, and
                 terminates because each adds its own height. A squiggle of ZERO
                 height would never terminate, and the symptom would be a sweep that
                 stops making progress with nothing in the log -- exactly the shape
                 EPG12's slur search range had. Upstream is protected by the music
                 font always carrying scripts.arpeggio; the port asks rather than
                 assumes, and reports. When the glyph is real the guard cannot fire
                 and the expression underneath it is upstream's, unchanged. This is
                 NOT one of the guards EPG15 is meant to remove: it is about a missing
                 glyph, not about spacing not having run.

  Figured_bass_position_engraver's assert becomes a programming error
                 Upstream asserts (!positioner_) on entry to start_spanner. The port
                 reports and returns rather than aborting the process, which is the
                 posture every other ported translator takes.

WHAT UPSTREAM DECLARES AND NEVER DEFINES

  Figured_bass_continuation::print is DECLARED in figured-bass-continuation.cc and
  has NO definition anywhere in the pinned tree. It is therefore NOT an entry point

  exactly ONE binding, ly:figured-bass-continuation::center-on-figures. Same shape as
  the Slur::vertical_skylines declaration EPG12 recorded -- and worth generalising: a

A DEFECT IN ALREADY-PORTED CODE, FOUND BY PORTING A CALLER

  ly_assoc had never been carried, and SchemeUtilities.LyAssocGet carried a RECORDED
  NARROWING in its place: it went straight to Assq, so a key that is neither a symbol
  nor an immediate was compared by IDENTITY where upstream compares by equal?. The
  note said "no caller in the engine uses such a key today". Drum_notes_engraver is

    needs the pages back. Scheme callers that ignore the result -- every one in
    ly/init.ly -- are unaffected. Both bindings FORCE the pages before
    returning, because a lazily-empty paper book is indistinguishable from a
    book with nothing in it.

  page-turn-page-breaking.cc -- print_break_node is not ported. It exists only
    behind -ddebug-page-breaking-scoring, which this port does not carry.

  page-layout-problem.cc -- the spacing-spec readers (is_spaceable,
    read_spacing_spec, get_spacing_spec, get_fixed_spacing, add_stretchability)
    stay in Layout/PageLayoutSpacing.cs, where EPG7 pulled them forward because
    Align_interface reads every adjacent pair of staves through them. They are
    NOT duplicated here.

TRAPS WORTH NOT REDISCOVERING (EPG16)

  THE UNSIGNED-VPOS TRAP IS REAL AND IT COST THIS SESSION A SWEEP.
    Page_spacer::calc_subproblem guards its cell update with
    `if (page > 0 || page_start == 0)'. When the page count is UNCONSTRAINED
    upstream passes page = VPOS, which is the LARGEST unsigned value, so
    `page > 0' is TRUE. Ported literally against NoPosition (-1) the test
    INVERTS: the only cell ever written is page_start == 0, so every line's best
    solution becomes "put lines 0..line on ONE page" and the unconstrained
    solver answers a single page for any book of any height. It is not a subtle
    mis-scoring -- it is the entire page-breaking decision, and it fails
    silently with a plausible-looking page. Every `> 0' and `< size' test
    against a vsize that may hold VPOS needs reading twice.

ADDED 2026-08-09 (EPG16 CLOSE-OUT) -- FIVE BINDINGS THAT WERE NEVER REGISTERED
-------------------------------------------------------------------------------

Every defect this session found was in code whose LEDGER ROW ALREADY SAID
`ported', and every one of them was silent. The shape repeats often enough now
to state as a rule:

  A PORTED TYPE WITH AN UNREGISTERED BINDING IS WORSE THAN AN UNPORTED TYPE.
  The C# side works, every C# caller works, the ledger row is honest about the
  FILE, and the Scheme side quietly receives an UnportedValue placeholder --
  which is inert, so it flows politely through whatever asked for it. Nothing
  fails. PORT-COVERAGE's own EPG0-era note predicted this in as many words
  ("one Scheme call away from being actively wrong"); it took until EPG16 to
  come true, twice.

  ly:context-def-modify, ly:context-def-lookup  (context-def.cc)

    NEITHER WAS REGISTERED. Context_def itself was ported whole -- Clone,
    AddContextMod, Lookup and IsAlias all existed -- so both bindings are
    one-line calls onto methods already there.

    The cost was not a missing feature. lily-library.scm's
    `context-defs-from-music', which EVERY toplevel \layout block containing a
    context modification runs through, does

        (ly:output-def-set-variable! output-def (car entry)
                                     (ly:context-def-modify (cdr entry) mods))

    so each context definition the block touched was OVERWRITTEN with the
    placeholder. Measured: `\layout { \override StaffSymbol.staff-space = 1.23 }'
    took the layout from 43 context definitions to 20 -- every one of the 23
    that answer to `Bottom' destroyed -- and `\layout { \markLengthOn }'
    destroyed all four that answer to `Score'. The score then had no context to
    engrave into and the file produced NO PAGES AT ALL. The only diagnostic was
    "cannot create default child context: Voice", which names neither the
    \layout block, nor the binding, nor the context definitions.

    Seven regression files were dying this way. A plain `\layout { ragged-right
    = ##t }' was unaffected, which is what made the defect look absent: a
    variable assignment never reaches context-defs-from-music at all.

  ly:system::get-staves, ly:system::get-spaceable-staves,
  ly:system::get-nonspaceable-staves  (system.cc)

    One upstream function under a filter, and its only caller is
    paper-system.scm's `paper-system-annotate', which takes (length ...) of the
    answer on the very next line. So `\paper { annotate-spacing = ##t }' -- two
    words -- took the whole book down with wrong-type-arg ("length" "Not a
    proper list"), naming neither the paper variable nor the callback.

    Registered here with EPG16 rather than with system.cc's other callbacks
    because they are page-layout surface: annotate-spacing is what wants them.

THE DEPRECATED-PROPERTY PATH WAS ONLY HALF PORTED (lily-guile.cc)

  Deprecated_property::getter_desc was wired into ly:context-property. The
  SETTER half -- internal_type_check's deprecation branch and type_check_unset
  -- was not, and SchemeUtilities.TypeCheckAssignment said so in a comment:
  "until the deprecation path is ported the property is simply unknown".

  The cost was that `\unset Timing.<deprecated>' was DISCARDED. A file that set
  skipTypesetting, then unset it through the deprecated alias, never turned
  typesetting back on -- and engraved nothing at all, with no diagnostic.

  Two structural changes came with it, both required rather than incidental:

  * THE PREDICATE LOOKUP NOW COMES FIRST. The port ran value_type_check's
    short-circuits ('()/#f/*unspecified*, and backend-type?'s procedures) BEFORE
    asking whether the property exists, so an unknown name carrying any of those
    values was accepted in silence -- and the deprecation branch was unreachable
    for exactly the case that needs it most, since \unset passes no value at
    all. Upstream asks for the predicate first; only a property that HAS one
    gets the short-circuits.

  * TypeCheckAssignment ANSWERS A SYMBOL AND A VALUE, not just a bool. A
    deprecated property redirects to its replacement AND converts its value on
    the way (the description carries an old->new function precisely because a
    rename is not always only a rename). The bool overload is kept for
    backend-type? and music-type?, the two categories scm/lily.scm leaves
    unwired, and says in its own doc why it is safe there and nowhere else.

  DeprecatedProperty now threads the CATEGORY through
  deprecated-setter-object-property instead of hardcoding the translation
  table, which is upstream's indirection and exists so a backend or music
  deprecation table can be added without silently consulting the wrong one.

ly:grob-system USED THE WRONG FUNCTION ON THE WRONG AXIS (grob-scheme.cc)

  grob-scheme.cc:349 calls the VIRTUAL me->get_system(): Grob answers 0, Item
  answers from its X parent, Paper_column answers the system it was assigned,
  and Spanner (spanner.cc:336) answers from its TWO BOUNDS when both agree. The
  port instead walked Y PARENTS -- which is not that function, and is not
  upstream's static Grob::get_system(Grob *) helper either, since that walks X
  parents and is documented as the PRE-line-breaking version.

  All four levels of the virtual were already ported correctly. Only the
  binding was wrong, so a spanner whose bounds knew their system still answered
  nothing. Second half of the same divergence: upstream answers SCM_EOL, the
  port answered #f, and '() is TRUE in Scheme -- so `(and (ly:grob-system g)
  ...)' took different branches in the two.

  ⚠ FIXING THE TRUTHINESS ALONE FIXES NOTHING, and the previous session's note
  said so: bar-line.scm hands the answer to ly:grob-extent, which rejects '() as
  firmly as #f. The first half is the substantive one. Three ratchet rows came
  back with it.

THE KEEP-THE-PARSER-CURRENT WRAPPER DOES NOT RETIRE (BatchRunner)

  EPG16 inherited it as item 3 of three, on the premise that moving the runner
  onto the real ly:book-process path would make it unnecessary. THAT PREMISE IS
  WRONG AND WAS MEASURED WRONG on 2026-08-09: with the runner fully on the book
  path, removing the wrapper puts apply-output, fermata-dot-position,
  markup-rhythm-ragged and flags-straight-layout-staff-size straight back on
  "there is no current parser".

  The book path is not the parser's DYNAMIC EXTENT. Upstream reaches book
  processing from default-toplevel-book-handler, which the parser calls WHILE
  PARSING, so %parser is live by construction. This runner collects books
  during the parse and processes them after it, so it must publish %parser
  itself. AsCurrentParser is upstream's own fluid, not a workaround. Retiring
  it would mean processing each book from inside the toplevel handler, which is
  a design decision rather than a clean-up.

LilyPortEngraver's FIXED PADDING IS RETIRED (inherited item 2)

  The one-score API stacked a score's lines at a hardcoded 4.0. It now takes
  the offsets from the REAL Page_layout_problem, built with NO paper book and
  NO page -- upstream's own supported shape for a book-less problem, and the
  honest one here, because this API engraves one score against an UNSCALED
  layout and has no page to read system-system-spacing off. Anything wanting
  the paper's real spacing wants a book, and that path is BatchRunner.

  BatchRunner's own StackSystems was DEAD CODE by then and is deleted.

⚠ Bezier IS A CLASS IN Flower, SO UPSTREAM'S COPY-ON-ASSIGN NEEDED WRITING OUT

  vaticana-ligature.cc's flexa maker is built on

    Bezier top_curve = curve, bottom_curve = curve;

  which COPIES in C++ and would ALIAS in C#, because Flower's Bezier is a sealed
  class rather than a struct. All three names would be the same object and every
  control-point adjustment would land on all three, silently, producing a
  degenerate shape rather than an error. VaticanaLigature.CopyOf makes the copy
  explicit and is commented as load-bearing at both ends.

  This is a defect CLASS, not one site: any port of upstream code that assigns a
  Bezier by value has it. No other current site does -- checked -- but the next
  one will.

from_scm<bool> IS EXACTLY-#t, AND THIS GROUP DEPENDS ON IT

  scm_conversions<bool>::from_scm defaults its fallback to false, which makes it
  scm_is_eq (s, SCM_BOOL_T) -- NOT Scheme truth. Gregorian_ligature_engraver
  MULTIPLIES the result by a bit mask, so a truthy-but-not-#t value would have to
  come out 1 anyway; but Mensural_ligature_engraver branches on ligature-flexa,
  ligature-pes, left-down-stem, right-down-stem and right-up-stem, and there an
  unset property read as true would change every shape in the ligature. The port
  uses SchemeUtilities.ToBool (exactly-#t) throughout, never IsSchemeTrue -- the
  defect class the 2026-08-08 CARRY-FORWARD session named.

PITCH READS FALL BACK TO 0 WHERE UPSTREAM DEREFERENCES A NULL

  calc_delta_pitches, provide_context_info, Mensural_ligature_engraver's
  transform_heads and Vaticana_ligature_engraver's ambiguous-dot check all read

    unsmob<Pitch> (get_property (cause, "pitch"))->steps ()

  with no null check. Upstream segfaults if a ligature primitive has no pitch;
  the port answers 0. The case is unreachable in valid input -- rests are refused
  by acknowledge_rest and transform_heads checks note-event before it reads the
  pitch -- so this is a crash-safety choice, not a behaviour change.

THIRD-PARTY SOFTWARE NOTICES AND INFORMATION

CodeBrix.LilyPort is a .NET-10 port of LilyPond 2.27.2 -- the GNU music
typesetter. Because this project is a port, it incorporates source code
from LilyPond, and in time will incorporate the whole of it: the C++
engraving engine, the Scheme layer that drives it, the LilyPond input
language, and the music fonts.

This document is the complete attribution and licensing-compliance record
for this project. Every piece of third-party code, data, script, font, or
asset that has been adapted, copied, or pulled into CodeBrix.LilyPort is
recorded here, with its authors, source location, exact upstream revision,
license, the verbatim text of every notice that must travel with it, and
the list of files in this repository derived from it.

HOW THIS FILE IS MAINTAINED
--------------------------------------------------------------------------------

  1. This is a LIVING LEDGER. It is updated in the SAME COMMIT as any
     change that incorporates, adapts, modifies, or removes third-party
     source. It is never allowed to fall behind the code.

  2. LilyPond is NOT uniformly GPL-3.0-or-later. Audit of the upstream tree
     found FIVE distinct license regimes plus THREE third-party components
     it redistributes -- see section 1.1. Material is filed by its ACTUAL
     license, not by the project it arrived with. Note that one of those
     three, mf2pt1 (section 9), does NOT appear on upstream's own license
     exception list; it was found by auditing file headers directly.

  3. Section 2 records ly/articulate.ly, which is GPL-3.0-ONLY, not "or
     later". It IS included (Jeremy's ruling, 2026), and as a direct result the
     shipped NuGet package declares GPL-3.0-only. Our own sources remain
     GPL-3.0-or-later; only the aggregate is GPL-3-only. Flagged here rather
     than buried, because the two statements look contradictory and are not.

  4. Section 3 records fonts, which carry both a GPL font exception and a
     dual OFL option with Reserved Font Names. Reserved Font Names restrict
     what a modified font may be called.

  5. Nothing is summarised away. Where a notice must be reproduced in full,
     it is reproduced in full below, verbatim.

1.2  SCOPE OF THE PORT
--------------------------------------------------------------------------------

  Upstream components in scope, with sizes measured at v2.27.2:

    lily/              448 .cc files / 107,099 lines, plus 237 headers --
                       the engraving engine: grobs, contexts, iterators,
                       engravers, performers, layout, and the aesthetic
                       scorers
    flower/            8,655 lines -- utility library (Rational, Interval,
                       Offset, Polynomial, Matrix). No Guile dependency.
    lily/parser.yy     Bison grammar and Flex lexer for the LilyPond input
    lily/lexer.ll      language; 6,289 lines combined
    scm/               91 .scm files / 59,680 lines -- the Scheme layer
                       that drives the engine
    ly/                62 .ly files / 16,553 lines -- the LilyPond-language
                       standard library (SEE SECTION 2 for articulate.ly)
    input/regression/  2,146 .ly files -- the regression suite, which is
                       the only correctness oracle upstream provides;
                       there are no unit tests in lily/
                       (SEE SECTION 6 for the musicxml/ subtree)
    mf/                Metafont sources for the music fonts
                       (SEE SECTION 3 -- different license)

1.3  HOW PORTED FILES ARE MARKED
--------------------------------------------------------------------------------

  LilyPond is C++17 with a flat class layout and has no namespaces in the
  C# sense. The CodeBrix provenance comment therefore names the upstream
  FILE, and is followed by the modification notice that GPL-3 section 5(a)
  requires:

      namespace CodeBrix.LilyPort.<Area>; //was previously: lily/beam.cc;
      // Modified by Jeremy Ellis on <YYYY-MM-DD> as part of the CodeBrix port.

  The upstream top-of-file copyright header is preserved verbatim above the
  usings on every ported file. The per-file notice carried by LilyPond
  source, which must survive on every ported file, reads:

    This file is part of LilyPond, the GNU music typesetter.

    Copyright (C) <years> <author(s)>

    LilyPond is free software: you can redistribute it and/or modify
    it under the terms of the GNU General Public License as published by

--------------------------------------------------------------------------------
1.4  MODIFICATIONS MADE DURING THE PORT
--------------------------------------------------------------------------------

  * C++17 translated to C# targeting net10.0.
  * Boehm GC bookkeeping removed entirely. scm_gc_mark (146 call sites),
    scm_remember_upto_here* (46), scm_gc_protect_object /
    scm_gc_unprotect_object (7) and the smob apply hooks (2) have no
    analogue under .NET's precise, moving collector -- 201 call sites are
    deleted rather than translated.
  * The libguile C API replaced by CodeBrix.LilyScheme's managed
    equivalent. 280 distinct scm_* symbols across 4,101 call sites were
    measured in lily/ at v2.27.2 and form that library's API contract.
  * Scheme source (scm/, ly/) incorporated verbatim wherever possible.
    Minimising changes to LilyPond's Scheme is an explicit project goal;
    where a change is unavoidable it is recorded in section 9.
  * Bison/Flex grammar and lexer reimplemented for the managed pipeline.
  * The aesthetic scorers -- beam-quanting.cc, slur-scoring.cc,
    tie-formatting-problem.cc -- are translated FAITHFULLY rather than
    cleanly. They are demerit-scoring heuristics tuned over decades and
    are deliberately not refactored.

WHAT articulate.ly DOES

  It makes MIDI output musical. Articulation marks in notation are normally
  purely visual -- a staccato dot prints a dot, and playback ignores it.
  \articulate rewrites the music tree before performance so the marks are
  actually heard: notes are shortened by factors (staccato 1/2, staccatissimo
  1/4, portato 3/4, tenuto unchanged, unmarked 7/8), ornaments (trills, turns,
  mordents, pralls) expand into their constituent notes, and rall./accel./
  a tempo are observed.

  It touches NOTHING in the engraving path: zero references to grobs, stencils
  or \layout across all 973 lines.

  GPL-3-only and GPL-3-or-later material combine legally, but the COMBINED work
  can then only be conveyed under GPL version 3 exactly: the "or later" option
  cannot be exercised over a part that never granted it.

    * The NuGet package CodeBrix.LilyPort.GplLicenseForever declares
      PackageLicenseExpression = GPL-3.0-only (NOT GPL-3.0-or-later), and says
      so in its Description. Verified in the packed nuspec:

      say and what we grant over our own contribution. Only the AGGREGATE
      artifact conveys as GPL-3-only.

      BOTH STATEMENTS ARE TRUE AT ONCE. Do not "correct" either one to match the
      other; that is the most likely future mistake here.

    * The declaration was made BEFORE publishing rather than after. Publishing

WHY THE FONT IS A SEPARATE ENGINEERING PROBLEM, NOT JUST A SEPARATE LICENSE

  Emmentaler is not consumed as text. LilyPond addresses it by glyph name
  (noteheads.s2, clefs.G) and reads two CUSTOM OpenType tables, LILC and
  LILY, via lily/open-type-font.cc. These are zlib-compressed Scheme alists
  written at font-build time by mf/gen-emmentaler.fontforge.py, and they
  carry engraver-critical metadata: glyph extents in staff-space units,
  stem attachment points, and ledger shortening ranges, keyed by LilyPond
  glyph name as a Scheme symbol.

DECIDED (Jeremy, 2026): BUILD OUR OWN FONTS FROM THE METAFONT SOURCES

  binaries. (The prebuilt TEXT fonts ARE redistributed, by the separate
  decision D13 -- see section 10.)

  provenance is verifiable end to end from Metafont source to shipped
  binary. The build is a one-time operation whose OUTPUTS are committed; the

10.3  THE STANDING RULE FOR THESE 24 FILES: ASSETS FOREVER, NEVER EDIT
--------------------------------------------------------------------------------

  Subsetting, converting, or editing any of these files creates a DERIVED
  font: the GUST rename request wakes up, and AGPL source obligations
  attach to the modified version. If a face must ever change, it gets a
  new name and a new recorded decision. (This mirrors the Reserved Font
  Name rule for the music fonts in section 3.)

  The alias-chain tails (DejaVu, Noto CJK) that upstream's fontconfig
  falls through to are NOT bundled by upstream and are NOT vendored here.
  The port's fallback face is Roboto, consumed as the OFL-licensed
  CodeBrix.Platform.Fonts.Roboto NuGet package, pinned at version
  1.0.209.315 (decision D23; a version change is a deliberate
  re-baseline event)
  -- a package dependency, so nothing font-related beyond the 24 files
  above is vendored into this repository, and no further entry in this
  document is required for it. There is deliberately NO fallback to
  system fonts; scripts the chain does not cover render as missing-glyph
  .notdef output by design.

10.4  HOW THE FONT FILES ARE SHIPPED
--------------------------------------------------------------------------------

  All of the font binaries this project vendors -- the nine Emmentaler
  music fonts and their nine SVG companions covered by section 3, and the
  24 text faces covered by this section -- are compiled into the
  CodeBrix.LilyPort.Engine assembly as EMBEDDED RESOURCES, and therefore
  travel inside the published NuGet package rather than beside it.

  Nothing about the files themselves changes. They are embedded byte for
  byte, the sha256 manifests in assets/fonts/README.txt and
  assets/fonts/text/README.txt still describe exactly what ships, and the
  "assets forever, never edit" rule in section 10.3 is unaffected --
  embedding is not subsetting, converting or editing.

  What this means for the licenses:

    - The URW faces are AGPL-3.0 WITH the font-embedding exception, and
      the exception is written for precisely this: embedding the font, or
      unaltered portions of it, into another work does not place that work
      under the AGPL. Section 10.1 has the exception text.

    - The Emmentaler fonts carry the same style of exception under the
      GPL; see section 3.

    - Because the font files travel inside a binary rather than as loose
      files, the corresponding-source obligation in section 11 covers them
      too: the unmodified font binaries are in this repository under
      assets/fonts/, and that is where a recipient obtains them.

  Measured, and worth recording because it decides whether the font
  licenses reach the OUTPUT at all: the SVG backend embeds no font data in
  what it produces. Music glyphs are written as their own outline paths and
  text is written as text with a family name, so a document this project
  renders contains no copy of any font file.

10.5  THE TYPE 2 CHARSTRING INTERPRETER -- WRITTEN FROM THE SPECIFICATION
--------------------------------------------------------------------------------

  src/CodeBrix.LilyPort.Engine/Fonts/CffFont.cs
  src/CodeBrix.LilyPort.Engine/Fonts/CharstringRun.cs

  These two files read the Compact Font Format table of an OpenType font
  and execute its glyph programs, in order to measure the ink extent of a
  glyph -- a figure no font table records.

  They are NEW-IN-FAMILY code, written from the published format
  specifications (Adobe's "The Compact Font Format Specification" and "The
  Type 2 Charstring Format"). They are not a translation of, and carry no
  code from, FreeType, Pango, LilyPond, or any other implementation. A
  format specification is a description of a data layout, not a work these
  files derive from, so no third-party license attaches to them; they are
  covered by this project's own license like the rest of the new-in-family
  code.

  For the same reason they carry no upstream copyright header, per the
  provenance rule recorded in the plan's standing rules: new-in-family
  binding and support code states its derivation HERE rather than in a file
  header.

  The interpreter is validated against the SVG fonts vendored alongside the
  OTFs -- both were produced from one source by the font build -- so the
  answer key it is tested against is also material this document already
  covers, under section 3.

  BOUNDARY, recorded because it moved: CharstringRun.cs gained an
  IGlyphPathSink interface so a caller can receive the outline as drawing
  commands rather than as a string. That interface and its call sites are
  new-in-family like the rest of these two files. The CONSUMER that turns those
  commands into skyline segments is a translation of LilyPond's freetype.cc and
  therefore lives in its own file with upstream's copyright header --
  Fonts/GlyphOutlineSkyline.cs, listed in section 1.5. The split is deliberate:
  one file, one provenance.

11b. THE MERSENNE TWISTER (MT19937) -- ALGORITHM, NOT CODE
================================================================================

CodeBrix.LilyPort.Engine/Bootstrap/RandomPrimitives.cs contains a C#
implementation of the MT19937 pseudo-random number generator.

Provenance, stated precisely because standing trap 15b is about exactly this
kind of claim: the implementation was written for this port from the
PUBLISHED SPECIFICATION of the algorithm --

    Makoto Matsumoto and Takuji Nishimura, "Mersenne Twister: A
    623-dimensionally equidistributed uniform pseudo-random number
    generator", ACM Transactions on Modeling and Computer Simulation,
    Vol. 8, No. 1, January 1998, pp. 3-30.

-- and is NOT a copy or translation of the authors' reference implementation,
of libstdc++'s std::mt19937, or of any other existing source. The constants
(624, 397, 0x9908B0DF, the tempering masks, the 1812433253 seeding
multiplier, and std::mt19937's default seed of 5489) are the algorithm's
defining parameters and are not copyrightable expression.

Why it is here at all: upstream's lily/lily-random.cc holds a
std::mt19937 whose state ly:set-rand-seed sets and ly:make-tmpfile-name
draws from. .NET ships no MT19937, so porting those two entry points
faithfully required carrying the generator.

The bounded draw is NOT bit-identical to libstdc++'s: the reduction
std::uniform_int_distribution performs is implementation-defined by the C++
standard. This is recorded as a deliberate divergence in PORT-COVERAGE.txt.

12. RELATED REPOSITORIES AND THE SEPARATION OF MATERIAL
================================================================================

CodeBrix.LilyPort depends on CodeBrix.LilyScheme, a separate
LGPL-3.0-or-later library that carries its own THIRD-PARTY-NOTICES.txt
covering the GNU Guile material it incorporates.

The separation is deliberate and is a licensing decision, not a filing
convenience:

    LilyPond-derived source -> ONLY in CodeBrix.LilyPort    (GPL-3.0-or-later)
    Guile-derived source    -> ONLY in CodeBrix.LilyScheme  (LGPL-3.0-or-later)

Keeping LilyPond material out of CodeBrix.LilyScheme keeps that library
usable on its own terms: LGPL-3 permits a proprietary or permissively
licensed consumer to link against it, which GPL-3 would not. A single
LilyPond-derived file placed there would forfeit that permanently.

This project, being GPL-3, may consume LGPL-3 material freely; the
combination is explicitly contemplated by LGPL-3 section 2.

Fresco.Brix, the Frescobaldi port that shares this repository, is a
separate work with its own upstream (Frescobaldi, GPL-2.0-or-later) and
will carry its own attribution records. Nothing in this document covers it.
